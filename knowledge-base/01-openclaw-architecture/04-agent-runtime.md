# 04 — Agent 运行时

> Agent 是 OpenClaw 的"大脑":接收用户消息,调用 LLM + 工具,产出回复。本章只讲组件如何协作,不讲代码细节。

## 组件清单

Agent 运行时由 7 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **Agent Runner** | 一次 agent run 的总编排,串联 8 个阶段 | 阶段顺序固定,trace 贯穿全程 |
| **Lane 调度器** | 控制并发:同 session 串行,跨 session 并发 | 防止单 agent 多任务竞争 |
| **Provider 运行时** | 调用 LLM,处理 auth、流式返回 | 由插件提供,核心不绑定特定厂商 |
| **Tool 注册表** | 收集插件注册的工具,注入 LLM 请求 | 工具表确定性排序(prompt cache 友好) |
| **终态归一化器** | 把"正常 / 超时 / 取消 / 错误"归一为单一终态 | **硬约束:禁止在其他地方重推优先级** |
| **Agent 状态库** | per-agent SQLite,存会话历史 / 运行记录 / 缓存 | 所有状态落库,无内存态泄漏 |
| **回复分发器** | 把回复送回原 channel | 走插件 Hook,不直接调 channel |

### Lane 调度的并发模型

```
                 Agent 任务到达
                       │
                       ▼
           ┌───────────────────────┐
           │  Lane 调度器          │
           │  按 agent + session   │
           │  分配 lane            │
           └───────────┬───────────┘
                       │
         ┌─────────────┼─────────────┐
         ▼             ▼             ▼
   ┌───────────┐ ┌───────────┐ ┌───────────┐
   │  Lane 1   │ │  Lane 2   │ │  Lane 3   │
   │  agentA   │ │  agentB   │ │  agentA   │
   │  sess-1   │ │  sess-1   │ │  sess-2   │
   └─────┬─────┘ └─────┬─────┘ └─────┬─────┘
         │             │             │
         ▼             ▼             ▼
     [执行中]      [执行中]      [执行中]
     (并发)        (并发)        (并发)
                              ↑
                  同 agent 不同 session 可并发
                  同 session 串行(避免竞争)

   设计目的:
   • 避免单 agent 多任务竞争
   • 跨 agent 完全并发
   • Lane 数有上限,防资源耗尽
   • Lane 间不互相阻塞
```

## 协作流程

### 一条消息的完整旅程

下面追踪一条用户消息从接入到回复的全过程,标注每步由哪个组件负责。

```
用户在 Telegram 发了 "帮我查天气"
         │
         ▼
┌─────────────────────────────────────────────────────────────┐
│ 1. Channel 接入层                                            │
│    Telegram 插件收到消息,转成 OpenClaw 内部格式              │
│    → 提交给 Gateway                                          │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Lane 调度器                                               │
│    按 agentId + sessionKey 分配 lane                        │
│    → 同 session 排队等(如有前序任务),跨 session 立即执行   │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. Agent Runner 接管                                         │
│    ① trace.mark('start')  ← 启动可观测追踪                  │
│    ② 解析注入依赖(logger / store 等)                       │
│    ③ 加载 agent 配置(用哪个模型、auth profile)              │
│    ④ 准备 session,绑定 per-agent SQLite                    │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. Provider 运行时                                           │
│    → 从 Tool 注册表拿工具表(确定性排序)                    │
│    → 拼 prompt(含会话历史)                                │
│    → 调用 LLM(如 OpenAI / Anthropic)                       │
│    → 流式返回 chunk                                          │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 5. 流式接收 + Tool Call 循环                                 │
│    ┌─────────────────────────────────────────────┐         │
│    │  循环直到 LLM 完成:                          │         │
│    │  ├─ 收到 chunk → 累积到回复                  │         │
│    │  └─ 收到 tool call →                       │         │
│    │      同步执行插件 Tool Hook                │         │
│    │      → 把工具结果送回 LLM                  │         │
│    │      → 继续接收下一轮 chunk                │         │
│    └─────────────────────────────────────────────┘         │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 6. 终态归一化(硬约束)                                       │
│    输入信号:正常完成 / 超时 / 用户取消 / 错误               │
│    → 经单一入口归一为统一终态                               │
│    → 包含:终态类型 / 原因 / 可观测指标 / 是否可重试         │
│                                                             │
│    ⚠ 禁止在 projections 等其他地方重新推导优先级            │
│      (否则 timeout + cancel 同时发生时各处会给出不同结果)  │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 7. 落库 + 回复分发                                           │
│    → 状态写入 per-agent SQLite(会话历史 / 运行记录)        │
│    → 回复分发器把回复送回 Telegram 插件                     │
│    → Telegram 插件把回复发到用户                             │
└────────────────────────────┬────────────────────────────────┘
                             ▼
                  trace.mark('end')
                  用户看到 "北京今天 28°C 晴"
```

### 终态归一化的优先级问题

为什么必须用单一入口?下面用反例说明。

```
场景:用户在 LLM 还没回完时点了"取消"
       同时,LLM 调用也超时了

错误做法(各自判断):
┌─────────────────────────────────────────────┐
│ Projection A(看超时)   → 终态: timeout   │
│ Projection B(看取消)   → 终态: cancel    │
│ Projection C(看完成度) → 终态: partial   │
└─────────────────────────────────────────────┘
→ 同一次 run,不同视角看到不同终态 → 数据不一致

正确做法(单一归一化入口):
┌─────────────────────────────────────────────┐
│ 所有信号 → 终态归一化器 → 单一终态         │
│ 优先级表只在这里定义一次                     │
│ → 所有 projection 读同一个终态 → 一致        │
└─────────────────────────────────────────────┘
```

## 关键设计约束

### 1. 终态归一化是硬约束

> Agent run terminal state: normalize/merge via 终态归一化器; do not rederive timeout/cancel precedence in projections.

- **为什么**:防止散落的优先级判断产生不一致
- **怎么做**:所有终态信号(超时/取消/错误/正常)必须经单一入口归一化
- **影响**:projections 只能读归一化后的终态,不能自己判断

### 2. Lane 并发模型

- **同 session 串行**:避免同会话多任务竞争状态库
- **跨 session 并发**:不同会话互不阻塞
- **Lane 数有上限**:防止资源耗尽

### 3. 依赖注入便于测试

Agent Runner 通过依赖注入接收 logger / store 等,测试时可替换为 stub。
- **为什么**:便于单元测试隔离
- **怎么做**:不直接 `import`,而是从参数接收

### 4. 状态全部落库

- 所有会话历史、运行记录、缓存都写入 per-agent SQLite
- **无内存态泄漏**:进程重启后状态可恢复
- **Session 与状态库绑定**:sessionKey 决定使用哪个 agent 的库

### 5. Trace 贯穿全程

- 每个阶段都打 mark(start → 各阶段 → end)
- **用途**:性能分析、调试、可观测性
- **不能省略**:这是排查 agent run 问题的核心依据

## 设计观察

### 为什么 Agent Runner 不直接调 LLM

```
错误设计:
   Agent Runner ──直接调用──► OpenAI API

正确设计:
   Agent Runner ──► Provider 运行时 ──► LLM
                         ▲
                         │
                    插件系统(可替换)
```

- Provider 由插件提供,核心不绑定特定厂商
- 切换 LLM 厂商只需换 Provider 插件,Agent Runner 不变
- 同一个 Agent 可配置不同 Provider(OpenAI / Anthropic / 本地)

### 为什么 Tool 由插件注册而非硬编码

- 工具表从插件 Hook 收集,Agent Runner 不预知有哪些工具
- 新增工具 = 新增插件,不改 Agent Runner
- 工具表确定性排序 → prompt cache 友好(相同输入产生相同 cache key)
