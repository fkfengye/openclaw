# 00 — 配置层总览

> 这是配置子目录的入口。读完本章你将理解:配置层为何存在、它由哪三步加载构成、IO 操作与类型系统与 Schema 变更三组组件如何协作,以及配置层为整个运行时提供什么契约。

## 一句话定位

配置层是 OpenClaw 运行时的"事实来源"——
- 它把磁盘上的单个配置文件 + 环境变量,转化为运行时可消费的规范形态
- 加载走固定的三步:读取 → 迁移 → 校验,核心只认最新形态
- 旧形态不进运行时,只在 doctor 迁移代码里被修平

## 组件清单

配置层由三大类、共约 26 个组件协作。下表只列层级别;每层细节见下属章节。

| 组件(层) | 职责 | 关键约束 |
|---|---|---|
| **IO 操作层** | 读磁盘配置、做快照、原子写入、审计留痕、健康观测、灾难恢复 | 核心只读最新形态;写入必须原子且留审计 |
| **类型系统层** | 为所有配置区块定义 TS 类型与枚举契约(认证/自动化/渠道/MCP/工具等) | 类型是 exported 契约,变更须与 schema/help/文档对齐 |
| **Schema 与变更层** | 把类型转成 JSON Schema 元数据、应用字段帮助/标签、物化默认值、校验、执行作用域变更、合并补丁、检测遗留 key | Retired key 保持 retired;兼容只在 doctor/迁移代码 |

### 三层之间的依赖方向

依赖是单向的:下层不感知上层,上层组合下层。类型系统层是 IO 层与 Schema 变更层的共同底座。

```
   ┌──────────────────────────────────────┐
   │  IO 操作层                           │
   │  (读取/写入/恢复)                    │
   └──────────────────┬───────────────────┘
                      │ 依赖
                      ▼
   ┌──────────────────────────────────────┐
   │  类型系统层                          │
   │  (形态契约)                          │
   └──────────────────┬───────────────────┘
                      │ 被依赖
                      ▼
   ┌──────────────────────────────────────┐
   │  Schema 与变更层                     │
   │  (校验/改写)                         │
   └──────────────────────────────────────┘

   反例(禁止):
   类型系统层 ──import──► IO 操作层
   → 底层反向依赖上层 → 循环 + 难以测试
```

## 协作流程

### 一次配置加载的完整旅程

下面追踪 Gateway 启动时加载配置的全过程,标注每步由哪类组件负责。

```
Gateway 启动到"加载配置"阶段
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. IO 操作层 — 装配上下文                                      │
│    IO 工厂组装依赖:文件系统句柄、环境、日志器、状态库连接      │
│    → 确定配置文件路径                                          │
│    → 准备校验用的插件元数据快照加载器                          │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. IO 操作层 — 读取快照                                       │
│    若文件不存在 → 用空配置 + 迁移默认 roster                  │
│    若文件存在 → 解析(JSON5 + 注释)                          │
│    → 展开 include 指令(组合多文件)                          │
│    → 注入环境变量(占位符替换)                               │
│    → 计算快照指纹(hash)                                      │
│    → 同时检测:来自未来版本的配置、误写的 key                 │

                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. Schema 与变更层 — 迁移与物化                                │
│    → 检测遗留 key(收集为遗留问题清单,不静默改写)            │
│    → 物化默认值(日志/会话/模型/agent/cron/消息)             │
│    → 路径归一化(跨平台规范化)                               │
│    → 旧隐式 main roster 迁移为显式形态                       │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. Schema 与变更层 — 校验                                     │
│    → 用 JSON Schema 合约校验整体形态                         │
│    → 渠道规则检查(DM 策略依赖、绑定限制等)                  │
│    → 插件配置 + manifest 元数据交叉校验                      │
│    → 校验失败:抛出含字段路径与修复建议的错误                 │
│    → 校验通过:产出规范化运行时配置对象                       │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 5. IO 操作层 — 观测与留痕                                      │
│    → 健康观测器记录本次读取的指纹/时间戳                      │
│    → 审计日志追加读取记录(可追溯)                          │
│    → 若一切正常 → 推进为 last-known-good 快照                │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 6. 下游消费                                                   │
│    → 规范化配置对象递交给 Gateway 启动编排                    │

└──────────────────────────────────────────────────────────────┘
```

### 一次配置写入的完整旅程

写入不是简单"覆盖文件",而是带快照竞争检测、原子落盘、审计留痕的完整流程。

```
某处请求改写配置(如 CLI set / 插件变更)
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. Schema 与变更层 — 构建变更                                 │
│    → 选定变更基线(runtime 或 source 形态)                   │
│    → 用合并补丁生成增量(RFC 7396 风格)                      │
│    → 应用作用域内的 unset 路径                                │
│    → 环境变量引用保护(避免把 ${VAR} 写死成值)               │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. IO 操作层 — 乐观快照竞争                                   │
│    → 读取当前快照指纹                                         │
│    → 与变更发起时的基线指纹对比                               │
│    → 不一致 → 抛出冲突错误(可重试,不盲写)                  │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. IO 操作层 — 校验后写入                                     │
│    → 写入前重新校验(改完也得合法)                          │
│    → 原子替换文件(旧文件不留半写)                          │
│    → 维护备份轮转(保留历史可回滚)                          │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. IO 操作层 — 审计留痕                                       │
│    → 追加写审计记录(谁/何时/改了哪些路径/原值)             │
│    → 记录写入元数据(进程信息)                               │
└──────────────────────────────────────────────────────────────┘
```

## 关键设计约束

### 1. 核心只支持最新配置形态

- **为什么**:运行时兼容旧形态会让"当前形态"的边界模糊,散落的 fallback 难以维护与排查
- **怎么做**:运行时只读取当前规范形态;旧形态在 doctor 迁移代码里被修平后才进入运行时
- **影响**:不做运行时 shim、alias、fallback reader;升级用户须先跑 doctor

### 2. 运行时无静默兼容

- **为什么**:静默兼容会把"用户以为生效但实际没生效"的隐患藏起来,违背可观测性
- **怎么做**:不读旧/畸形 key,不留 dual-write 或 read-through fallback;retired key 保持 retired
- **影响**:配置契约变更必须配 doctor 迁移;否则用户升级会直接报错而非"静默忽略"

### 3. 配置契约须四向对齐

- **为什么**:类型、schema/help、元数据、基线、文档任一偏离都会让用户在 UI 看到的帮助与实际行为不符
- **怎么做**:exported 类型、schema 帮助文本、字段标签、文档基线在同一次变更中保持对齐
- **影响**:改类型必须同时审视 schema 帮助与文档基线

### 4. 配置/环境变量表面门槛高

- **为什么**:openclaw.json 与环境变量已经很大,新增项会放大复杂度与升级风险
- **怎么做**:新增前先证明现有行为、provider 选择、默认值或 doctor 迁移无法解决
- **影响**:优先删减/合并而非新增;新增须证明必要性

### 5. CLI setup 流程是公开 API

- **为什么**:安装器、外部文档、集成会复制 onboard/configure 的命令与生成形态
- **怎么做**:变更走 additive flag + 弃用窗口 + 向后保留迁移,而非破坏式改写
- **影响**:非交互行为与生成的配置形态属于兼容敏感的 API 契约

### 6. 状态存储仍是 SQLite

- **为什么**:配置层的健康状态、审计记录、last-known-good 快照都是运行时状态,不能散落成文件
- **怎么做**:配置健康指纹、审计记录写入共享状态库;禁止 JSON/sidecar 存这些运行时状态
- **影响**:进程重启后健康观测可恢复;不存在"状态文件与实际不一致"

## 设计观察

### 为什么配置走"读取-迁移-校验"而非"读取-即用"

```
错误设计:
   读文件 ──► 直接用
   → 旧 key 混进运行时 → 各处都要写防御性分支
   → 默认值散落在消费方 → 不一致

正确设计:
   读文件 ──► 迁移(默认值/路径/roster)──► 校验 ──► 用
   → 旧 key 在迁移阶段就被识别并报告
   → 默认值集中物化一次
   → 消费方拿到的永远是合法规范形态
```

### 为什么写入要做乐观快照竞争

```
危险场景:用户在 CLI 改配置的同时,Gateway 正在自动写配置

错误做法:直接覆盖文件
   → 一方丢失另一方的改动 → 静默数据丢失

正确做法:变更时记基线指纹,写入前对比当前指纹
   → 不一致 → 抛冲突错误(可重试)
   → 强制重读最新 → 永不静默覆盖
```
