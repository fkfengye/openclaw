# 01 — 配置 IO 操作

> 配置层的最底层。读完本章你将理解:配置如何被读取为快照、如何在竞争与灾难下被安全写入、健康观测如何发现可疑文件、以及 last-known-good 如何在文件被破坏时救命。

## 一句话定位

IO 操作层是配置层与文件系统之间的全部边界——
- 所有磁盘读写、快照、审计、恢复都收口在这里
- 它把"读文件"这件看似简单的事,扩展成带指纹、带观测、带灾难恢复的可观测流程
- 上层(Schema/类型/变更器)只拿到规范化的快照对象,不直接碰磁盘

## 组件清单

IO 操作层由 8 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **IO 工厂** | 组装依赖、暴露统一的读/写/恢复入口 | 依赖可注入,便于测试隔离 |
| **IO 上下文** | 持有文件系统句柄、环境、路径、选项;承载物化与校验的回调 | 一个上下文贯穿一次配置生命周期 |
| **快照读取器** | 解析文件、展开 include、注入环境变量、生成快照指纹 | 失败不静默;收集遗留问题而非改写 |
| **健康观测器** | 比对本次与上次指纹、标记可疑(丢失/损坏/被覆盖)、写健康状态 | 健康状态落状态库,不存文件 |
| **审计记录器** | 记录每次读/写事件的进程信息、路径、参数(脱敏后) | 参数与路径有上限,防日志爆炸 |
| **灾难恢复** | 文件被破坏时从 last-known-good 快照恢复 | 仅在策略判定可恢复时触发;留审计 |
| **最佳努力恢复** | 处理 JSON 根偏移、半截文件等结构异常 | 容错读最近的有效 JSON 根 |
| **安全写入器** | 乐观竞争检测、校验后写、原子替换、备份轮转、审计留痕 | 写入前必校验;不一致则抛冲突可重试 |

## 关联关系

### 读取与观测的并行协作

读取与观测不是串行的两步,而是在读取过程中持续记录,读取完成后由观测器决定是否推进为已知良好。

```
   ┌──────────────┐
   │ 磁盘文件     │
   └──────┬───────┘
          │ 读
          ▼
   ┌────────────────────────┐
   │ 快照读取器              │
   │ • 解析 → 展开 → 注入    │
   │ • 边读边收集遗留问题    │
   │ • 算指纹                │
   └───────────┬────────────┘
               │
               ▼
   ┌────────────────────────┐
   │ 健康观测器              │
   │ • 与上次指纹比对        │
   │ • 不一致 → 标记可疑     │
   │ • 可疑 → 触发恢复策略   │
   └───────────┬────────────┘
               │
      ┌────────┴────────┐
      │ 正常            │ 可疑
      ▼                 ▼
   ┌──────────┐    ┌─────────────────┐
   │ 推进为    │    │ 灾难恢复器      │
   │ last-known│    │ • 是否可恢复?  │
   │ -good     │    │ • 是 → 回滚     │
   └──────────┘    │ • 否 → 报错     │
                   └─────────────────┘

   反例(禁止):
   读取器自己判断"可疑"并自己回滚
   → 判定与恢复耦合 → 难以测试、策略散落
```

### 写入的乐观竞争模型

写入采用"乐观锁"思路:先记基线指纹,写前重读对比,不一致就放弃而非盲写。

```
   变更发起方持有基线指纹 X
            │
            ▼
   ┌──────────────────────────────┐
   │  写入前重读当前快照          │
   │  → 得到当前指纹 Y            │
   └──────────────┬───────────────┘
                  │
                  ▼
            X == Y ?
           /        \
         是          否
        /              \
       ▼                ▼
   ┌──────────┐    ┌──────────────────┐
   │ 校验变更 │    │ 抛冲突错误       │
   │ 原子写入 │    │ (标记可重试)     │
   │ 备份轮转 │    │ → 调用方重读重试 │
   │ 审计留痕 │    └──────────────────┘
   └──────────┘
```

## 协作流程

### 一次"文件被外部覆盖后"的恢复旅程

下面追踪配置文件被外部工具破坏后,IO 层如何检测、评估、恢复。

```
某进程(如文本编辑器/CI)把 openclaw.json 写坏成空或半截
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 快照读取器 — 读取发现异常                                 │
│    → 解析失败 / 指纹与上次健康指纹不符                       │
│    → 把快照交给健康观测器                                     │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 健康观测器 — 评估可疑程度                                 │
│    → 读取状态库里的健康状态(上次指纹、时间戳)              │
│    → 调用可疑原因解析器,给出具体原因                        │
│    → 写入新的健康状态条目(标记本次为可疑)                 │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 恢复策略判定                                              │
│    → 是否属于可恢复范围?(插件局部坏配置不在此恢复)         │
│    → last-known-good 是否存在且有效?                        │
│    → 是否值得冒险回滚?(避免回滚掉用户合法的改动)          │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 灾难恢复器 — 执行恢复                                     │
│    → 从 last-known-good 快照还原配置                         │
│    → 保留被破坏的快照(留作有界快照,供排查)                │
│    → 追加审计记录(原因:文件被覆盖)                        │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 5. 重新推进 last-known-good                                  │
│    → 恢复成功后,把恢复出的快照作为新的已知良好              │
│    → 健康状态回归正常                                         │
│    → 上层拿到一份合法配置,继续启动                          │
└──────────────────────────────────────────────────────────────┘
```

### 一次"CLI 修改配置项"的写入旅程

下面追踪用户用命令行修改某配置项时,IO 层如何安全落盘。

```
用户执行 CLI 配置修改命令
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 安全写入器 — 取变更基线                                    │
│    → 读取当前配置快照(用于写入的专用读取)                  │
│    → 记录当前快照指纹作为基线                                 │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 变更器 — 生成目标形态                                      │
│    → 应用 unset 路径(明确删除的字段)                       │
│    → 环境变量引用保护(保留 ${VAR} 形态,不写死值)         │
│    → 序列化为待写入文本                                       │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 安全写入器 — 乐观竞争检测                                  │
│    → 重新读取当前指纹                                         │
│    → 与步骤 1 基线对比                                        │
│    → 不一致 → 抛冲突错误(可重试,不覆盖)                   │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 安全写入器 — 校验后原子写入                                │
│    → 先校验目标形态合法(改完也得通过校验)                 │
│    → 原子替换文件(旧文件不留半写状态)                     │
│    → 维护备份轮转(保留若干历史版本)                       │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 5. 审计记录器 — 留痕                                          │
│    → 追加写审计记录:路径、原值、进程信息、来源标识          │
│    → 参数脱敏(不记录秘密值)                               │
│    → 记录写入元数据                                           │
└──────────────────────────────────────────────────────────────┘
```

## 关键设计约束

### 1. 健康状态落状态库,不落文件

- **为什么**:健康指纹是运行时状态;落成文件会产生"状态文件与实际不一致"的隐患,且与"SQLite 唯一状态层"的硬约束冲突
- **怎么做**:健康指纹、时间戳、可疑标记写入共享状态库
- **影响**:进程重启后观测可恢复;无散落 sidecar 文件

### 2. 读取失败收集问题而非静默改写

- **为什么**:静默改写旧/坏 key 会把"用户以为生效但实际没生效"藏起来,违背可观测性与无静默兼容原则
- **怎么做**:读取阶段把遗留 key 收集成"遗留问题清单",交给上层决定如何呈现;读取器自己不改写
- **影响**:用户能看到"哪些 key 已 retired"的明确报告

### 3. 写入必须先校验

- **为什么**:把非法配置写到磁盘,会让下次启动直接失败,且用户难以定位"何时被改坏"
- **怎么做**:写入器在落盘前对目标形态做完整校验;校验不过则拒绝写入
- **影响**:磁盘上的配置文件永远是合法形态(除非外部工具破坏)

### 4. 原子替换,不留半写

- **为什么**:进程在写入中途崩溃会留下半截文件,导致下次启动解析失败
- **怎么做**:写入临时文件 + 原子替换,而非直接覆盖原文件
- **影响**:即使写入过程中断,原文件保持完整

### 5. 乐观竞争优先于文件锁滥用

- **为什么**:长时间持锁会阻塞其他合法写入者;乐观竞争让大多数无冲突场景零等待
- **怎么做**:记基线指纹,写前重读对比;冲突时抛可重试错误而非阻塞等待
- **影响**:并发写入者不会互相饿死;冲突被显式暴露而非静默丢失

### 6. 审计参数脱敏且有上限

- **为什么**:审计记录可能含敏感参数或过长路径,直接记录会泄密或撑爆存储
- **怎么做**:秘密值脱敏;参数数量与路径长度有上限截断
- **影响**:审计可追溯但不泄密;存储增长有界

## 设计观察

### 为什么用"快照对象"而非"直接读文件"

```
错误设计:
   各处消费方直接读文件 → 各自解析 → 默认值散落
   → 同一份配置在不同消费方行为不一致
   → 没有指纹,无法观测变更

正确设计:
   快照读取器读一次 → 产出快照对象(含原始文本+解析结果+指纹+遗留问题)
   → 所有消费方共用同一份快照 → 行为一致
   → 指纹用于观测与竞争检测
```

### 为什么恢复要"保留被破坏的快照"

```
危险场景:文件被外部覆盖成坏内容,系统自动回滚

错误做法:回滚后直接丢弃坏快照
   → 用户不知道发生过什么 → 无法排查谁覆盖的

正确做法:回滚 + 把坏快照保留为"有界快照"
   → 留作排查证据(内容、时间)
   → 有界 = 数量上限,不会无限堆积
   → 审计记录里写明"因被覆盖而恢复"
```
