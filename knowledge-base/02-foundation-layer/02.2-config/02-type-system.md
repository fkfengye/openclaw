# 02 — 配置类型系统

> 配置层的形态底座。读完本章你将理解:OpenClaw 的配置如何被切成多个类型区块、基础类型如何被各渠道复用、每个区块约束什么行为,以及类型系统如何为校验器与 Schema 提供"可校验的契约"。

## 一句话定位

类型系统层是配置层的契约源——
- 它把"配置长什么样"用 TypeScript 类型固定下来,作为导出的公开契约
- 一个顶层类型聚合所有区块(认证、自动化、渠道、MCP、工具等)
- 类型与 schema/help/文档四向对齐,改一处须审视其余

## 组件清单

类型系统层由 10 类区块类型协作,加 1 类基础类型作为共享底座:

| 区块类型 | 职责 | 关键约束 |
|---|---|---|
| **基础类型** | 定义被多渠道复用的枚举与通用形态(回复模式、流式模式、群策略等) | 改动会影响所有渠道,需审视全部复用方 |
| **认证类型** | 定义 auth profile 的四种模式与排序偏好 | mode 是闭集;不引入未列出的新模式 |
| **ACP 类型** | 定义 ACP 会话调度、流式投递、运行时安装提示 | 会话更新可见性按 tag 覆盖 |
| **cron 类型** | 定义定时调度、失败告警、webhook 令牌、保留策略 | webhook 令牌走密钥输入,不直接存明文 |
| **hooks 类型** | 定义 hook 匹配、动作、唤醒模式、消息模板 | 危险开关需显式标注 |
| **MCP 类型** | 定义 MCP 服务器、传输方式、工具审批、过滤 | 审批模式是闭集 |
| **队列类型** | 定义入站消息的排队与丢弃策略 | 队列模式按 provider 分别配置 |
| **Slack 类型** | 定义 Slack 渠道的 DM、群、流式、反应等 | 复用基础类型,不重复定义枚举 |
| **工具类型** | 定义工具可用性、白名单、媒体理解作用域 | 群工具策略按发送者细化 |
| **TTS 类型** | 定义语音合成模式、自动触发、模型覆盖开关 | 模型覆盖默认关闭,需显式开启 |

## 关联关系

### 基础类型如何被各渠道复用

基础类型是"渠道无关"的通用契约。渠道类型只复用,不重复定义同名枚举,避免一处改两处漏。

```
   ┌──────────────────────────────┐
   │  基础类型                    │
   │  • 回复模式(text/command)   │
   │  • 流式模式(off/partial/    │
   │    block/progress)           │
   │  • 文本分块(length/newline) │
   │  • DM 策略(pairing/          │
   │    allowlist/open/disabled)  │
   └──────────────┬───────────────┘
                  │ 被复用
      ┌───────────┼───────────┐
      ▼           ▼           ▼
   ┌──────┐  ┌────────┐  ┌──────────┐
   │Slack │  │Telegram│  │ 其他渠道 │
   │ 类型 │  │  类型  │  │   类型   │
   └──────┘  └────────┘  └──────────┘

   反例(禁止):
   Slack 类型自己定义 "streamingMode" 枚举
   Telegram 类型自己定义另一个 "streamMode"
   → 两处枚举漂移 → 渠道行为不一致
```

### 顶层聚合类型的组装

顶层类型不是"一个大文件",而是从各区块类型聚合而来。新增区块 = 新增区块类型 + 在顶层引用。

```
   ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
   │ 认证   │ │ cron   │ │ hooks  │ │ MCP    │ ...区块类型
   │ 类型   │ │ 类型   │ │ 类型   │ │ 类型   │
   └───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘
       │          │          │          │
       └──────────┴──────────┴──────────┘
                       │
                       │ 聚合引用
                       ▼
          ┌──────────────────────────┐
          │  顶层配置根类型          │
          │  (公开的整份契约)       │
          └──────────────────────────┘
                       │
                       ▼
          ┌──────────────────────────┐
          │  校验器 / Schema / 物化器│
          │  (消费类型建合约)        │
          └──────────────────────────┘
```

### 密钥输入的统一形态

多个区块(cron webhook 令牌、Slack token、工具 exec 命令)都引用同一套"密钥输入"形态,而非各自定义字符串字段。

```
   ┌──────────────────────────────────────┐
   │  密钥输入类型(统一形态)             │
   │  • 字面量值  • 环境引用              │
   │  • 外部命令  • SecretRef            │
   └─────────────────┬────────────────────┘
                     │ 被引用
       ┌─────────────┼──────────────┐
       ▼             ▼              ▼
   ┌────────┐   ┌────────┐    ┌──────────┐
   │ cron   │   │ Slack  │    │ 工具 exec │
   │ webhook│   │ token  │    │ 命令     │
   └────────┘   └────────┘    └──────────┘

   好处:密钥解析逻辑只实现一次,所有区块复用
```

## 协作流程

### 一次"新增配置字段"的完整旅程

下面追踪给某区块新增一个配置字段时,类型系统如何与校验器、Schema、文档对齐。

```
需求:给 cron 区块新增一个"失败重试上限"字段
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 类型系统层 — 定义字段                                      │
│    → 在 cron 类型区块新增可选字段                            │
│    → 复用基础类型里的"重试配置"或新建(若语义不同)         │
│    → 标注注释说明语义                                         │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 顶层聚合 — 引用字段                                        │
│    → 顶层类型已通过区块聚合自动包含新字段                    │
│    → 确认导出契约更新                                         │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. Schema 与变更层 — 对齐                                     │
│    → 基础 Schema 生成器纳入新字段                            │
│    → 字段帮助文本补全(用于 UI 与文档)                      │
│    → 字段标签补全(用于分组筛选)                            │
│    → 校验器规则补全(值范围、依赖关系)                     │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 物化器 — 默认值                                            │
│    → 物化器在"应用默认值"阶段为新字段填默认                 │
│    → 不填默认则用户不写时为 undefined,行为须明确            │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 5. 文档基线 — 同步                                            │
│    → 文档基线快照更新(若该字段进入文档示例)                │
│    → help 文本与基线对齐                                     │
└──────────────────────────────────────────────────────────────┘
```

### 一次"枚举值收敛"的旅程

当某枚举需要收敛(删除一个旧值)时,流程更谨慎,因为旧值是 retired 公开契约。

```
需求:把某枚举的旧值 X 标记为不再支持
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 类型系统层 — 收敛枚举                                     │
│    → 从基础类型枚举中移除 X                                  │
│    → TS 编译期:所有写 X 的地方会报错                        │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 遗留检测 — 标 retired                                      │
│    → 遗留检测规则里登记:X 路径已 retired                    │
│    → doctor 迁移规则里加:把 X 改写为新值                   │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 校验器 — 拒绝旧值                                         │
│    → 校验器不再接受 X(它是非法值,不是静默忽略)            │
│    → 用户升级时:doctor 先把 X 迁走,运行时才不会撞到       │
└──────────────────────────────────────────────────────────────┘
```

## 关键设计约束

### 1. 枚举是闭集,不是自由字符串

- **为什么**:自由字符串会让"拼写错误"在运行时才暴露,且无法穷举所有合法值给 UI/文档
- **怎么做**:策略/模式类字段用联合字面量类型;校验器拒绝未列出的值
- **影响**:新增值须同步类型、schema、help、文档;不是随手加字符串

### 2. 基础类型是共享底座,渠道只复用

- **为什么**:若每个渠道各定义一套"流式模式/回复模式",枚举会漂移,渠道间行为不一致
- **怎么做**:渠道无关的通用枚举集中在基础类型;渠道类型只 import 复用
- **影响**:改基础枚举须审视所有渠道复用方;但保证全局一致

### 3. 密钥输入统一形态

- **为什么**:密钥解析(字面量/环境引用/外部命令/SecretRef)逻辑复杂,各区块重复实现会漂移
- **怎么做**:所有需要密钥的字段引用同一套密钥输入类型
- **影响**:密钥解析与脱敏只实现一次;新增区块无须重写

### 4. 危险开关须显式标注

- **为什么**:hooks 等区块有"允许不安全外部内容""模型覆盖"等危险能力,默认开启会引入安全风险
- **怎么做**:危险开关默认关闭,字段注释显式标 DANGEROUS
- **影响**:用户须主动开启才能降级安全;不会因漏写配置而暴露

### 5. 可选字段须明确 undefined 语义

- **为什么**:可选字段不写时行为若是"隐式默认",会让用户难以预测;若是"功能关闭",又与物化器默认值冲突
- **怎么做**:每个可选字段在类型注释里说明 undefined 时的行为;物化器集中填默认
- **影响**:消费方不靠"猜默认",物化器是默认值的唯一来源

### 6. 类型是导出的公开契约

- **为什么**:插件、SDK、外部工具会引用配置类型;类型签名一旦变化即破坏下游
- **怎么做**:类型变更视为兼容敏感的 API 变更;字段新增可加,字段删除/改类型需弃用窗口
- **影响**:与 CLI setup 流程同属"公开 API"门槛

## 设计观察

### 为什么类型按"区块"而非"一个大类型"组织

```
错误设计:
   一个巨型类型文件包含所有字段
   → 改 Slack 字段要在一个几千行文件里找
   → 职责不清,合并冲突频繁

正确设计:
   按业务区块切分类型文件(cron/hooks/mcp/slack/tools/tts...)
   → 每个区块职责单一,可独立审阅
   → 顶层只做聚合引用,改动局部化
   → 渠道插件可只引用自己关心的区块类型
```

### 为什么渠道类型不自己定义 DM 策略枚举

```
错误设计:
   Slack 类型定义 DmPolicy = "open" | "allowlist"
   Telegram 类型定义 DmAccess = "open" | "pairing"
   → 同一概念两个名字 + 不同取值集
   → 渠道间行为无法对齐,UI 无法统一展示

正确设计:
   基础类型定义 DmPolicy = "pairing" | "allowlist" | "open" | "disabled"
   → 所有渠道复用同一枚举
   → UI 可用统一筛选器
   → 新增渠道直接复用,无须重定义
```
