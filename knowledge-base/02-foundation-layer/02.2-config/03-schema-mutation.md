# 03 — Schema 与变更

> 配置层最顶层。读完本章你将理解:类型如何变成可校验的 Schema、字段帮助与标签如何供给 UI/文档、配置如何被物化为运行时就绪形态、变更如何安全落盘,以及遗留 key 如何被检测而非静默兼容。

## 一句话定位

Schema 与变更层是配置层的"出口与守门"——
- 它把类型系统的形态变成可校验的 JSON Schema 元数据,并附上帮助文本与标签
- 它把读取到的配置物化成运行时就绪形态(填默认值、归一化路径)
- 它执行作用域内的安全变更(合并补丁、乐观竞争、原子写入)
- 它检测遗留 key,但只在 doctor/迁移代码里改写,运行时不静默兼容

## 组件清单

Schema 与变更层由 8 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **基础 Schema 生成器** | 把类型转成 JSON Schema,递归应用字段文档 | 保留已有 title/description,不覆盖更丰富的元数据 |
| **字段帮助** | 为每个配置字段供给用户可读的帮助文本(用于 UI/文档) | 按区块分文件组织(core/runtime/model/agent/automation) |
| **字段标签** | 用稳定标签词汇为字段打标,供 UI 筛选分组 | 标签是闭集;有优先级排序 |
| **分层提示** | 识别敏感 URL/路径,在 Schema 上标注敏感路径提示 | 敏感路径不展示明文 |
| **物化器** | 把规范化配置填上默认值、归一化路径,产出运行时就绪形态 | 按模式(load/missing/snapshot)选不同默认值组合 |
| **校验器** | 用 Schema 合约校验整体形态,叠加渠道规则与插件交叉校验 | 失败报错含字段路径与修复建议;不静默放行 |
| **变更器** | 在作用域内构建并应用配置变更,委托 IO 层落盘 | 乐观竞争;变更前重校验;保护环境变量引用 |
| **合并补丁** | 生成与应用 RFC 7396 风格的增量补丁 | null 表删除;防原型链污染 |

## 关联关系

### Schema 元数据的三路供给

基础 Schema 不只是一个"结构描述",它把帮助文本、标签、敏感提示三路元数据合并到同一棵 Schema 树上,供 UI/文档/校验共用。

```
   ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
   │ 字段帮助文本 │  │ 字段标签    │  │ 分层敏感提示 │
   │ (按 dot-path)│  │ (闭集词汇)  │  │ (敏感 URL)   │
   └──────┬───────┘  └──────┬───────┘  └──────┬───────┘
          │                 │                 │
          └─────────────────┼─────────────────┘
                            │ 递归合并到 Schema 树
                            ▼
              ┌──────────────────────────────┐
              │  基础 Schema 生成器         │
              │  (保留已有 title/desc)      │
              └──────────────┬───────────────┘
                             │
              ┌──────────────┴───────────────┐
              │                              │
              ▼                              ▼
        ┌──────────┐                  ┌──────────┐
        │ UI/文档  │                  │  校验器  │
        │ 展示帮助 │                  │  用合约  │
        └──────────┘                  └──────────┘

   反例(禁止):
   帮助文本散落在 UI 代码里、标签硬编码在校验器里
   → 三处漂移 → 用户看到的帮助与实际行为不符
```

### 校验与物化的顺序

物化与校验不是任意顺序:物化在先(填默认值、归一化),校验在后(对物化后的形态做合约校验)。这样校验看到的是"运行时真正会用的形态"。

```
   读取到的规范化配置(可能缺默认值)
            │
            ▼
   ┌──────────────────────┐
   │ 物化器               │
   │ • 填日志默认         │
   │ • 填会话默认         │
   │ • 填模型/agent 默认  │
   │ • 归一化路径         │
   └──────────┬───────────┘
              │
              ▼
   ┌──────────────────────┐
   │ 校验器               │
   │ • Schema 合约校验    │
   │ • 渠道规则           │
   │ • 插件元数据交叉     │
   └──────────┬───────────┘
              │
              ▼
        运行时就绪配置
        (合法 + 完整)

   反例(禁止):
   先校验未物化的原始配置 → 默认值缺失报假错
   → 用户以为自己漏写,其实系统会补默认
```

### 变更器与 IO 层的分工

变更器只负责"构建变更并校验",真正的文件落盘委托给 IO 层(乐观竞争 + 原子写入 + 审计)。变更器不直接写磁盘。

```
   ┌──────────────────────────────────┐
   │  变更器                          │
   │  • 选基线(runtime/source)      │
   │  • 生成合并补丁                  │
   │  • 应用 unset 路径               │
   │  • 保护环境变量引用              │
   │  • 校验目标形态                  │
   └────────────────┬─────────────────┘
                    │ 委托落盘
                    ▼
   ┌──────────────────────────────────┐
   │  IO 层(安全写入器)             │
   │  • 乐观快照竞争                  │
   │  • 原子替换文件                  │
   │  • 备份轮转                       │
   │  • 审计留痕                       │
   └──────────────────────────────────┘

   好处:变更逻辑与文件 IO 解耦
   → 变更器可单测(不碰磁盘)
   → IO 层专注安全落盘(不关心变更语义)
```

## 协作流程

### 一次"配置加载中的校验失败"旅程

下面追踪配置文件里写错了一个字段值时,Schema 与变更层如何报出可操作的错误。

```
用户配置里把某枚举写成了拼写错误的值
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 物化器 — 物化                                              │
│    → 填默认值、归一化路径(物化不校验枚举合法性)            │
│    → 把(可能含非法值)的形态交给校验器                       │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 校验器 — Schema 合约校验                                  │
│    → 用基础 Schema 生成的合约校验整体                        │
│    → 发现该字段值不在枚举闭集内                             │
│    → 收集为校验问题(含字段 dot-path)                       │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 校验器 — 叠加规则                                          │
│    → 渠道规则检查(DM 策略依赖、绑定限制)                   │
│    → 插件配置 + manifest 元数据交叉校验                      │
│    → 合并所有问题                                             │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 抛出含修复建议的错误                                       │
│    → 错误信息含:字段路径、非法值、合法取值列表              │
│    → 用户可读(不是内部堆栈)                                │
│    → 加载失败,Gateway 启动中止(不静默放行)               │
└──────────────────────────────────────────────────────────────┘
```

### 一次"插件批量修改配置"的变更旅程

下面追踪某插件需要在一次操作里改多个配置字段时,变更器如何安全完成。

```
插件请求改写多处配置(原子:要么全成,要么全不改)
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 变更器 — 取基线                                            │
│    → 选定变更基线形态(runtime 或 source)                   │
│    → 在作用域内读取当前配置作为基线                         │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 合并补丁 — 生成增量                                        │
│    → 对比基线与目标,生成 RFC 7396 补丁                      │
│    → 删除的字段用 null 表示                                  │
│    → 防原型链污染(阻断危险 key)                            │
│    → 数组按需按 id 合并或整体替换                            │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 变更器 — 应用与保护                                        │
│    → 应用 unset 路径(明确删除的字段)                       │
│    → 保护环境变量引用(保留 ${VAR},不写死值)              │
│    → 校验目标形态合法                                        │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 委托 IO 层 — 乐观竞争 + 原子写入                           │
│    → 读取当前指纹,与基线指纹对比                            │
│    → 不一致 → 抛冲突错误(可重试)                          │
│    → 一致 → 原子写入 + 备份轮转 + 审计留痕                 │
└──────────────────────────────────────────────────────────────┘
```

### 一次"用户带着旧配置升级"的遗留检测旅程

下面追踪用户升级版本后,旧配置里的 retired key 如何被识别与引导迁移。

```
用户升级到新版本,旧 openclaw.json 里有 retired key
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 读取阶段 — 配置进到校验与物化                              │
│    → 旧 key 仍在原始配置里(读取不删它)                     │

                             ▼

│ 2. 遗留检测 — 收集问题清单                                   │
│    → 用内置遗留规则 + doctor 共享迁移规则扫描               │
│    → 按原始 dot-path 定位每个 retired key                   │

                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 运行时 — 不读 retired key                                 │
│    → 运行时只认最新形态,retired key 被忽略(不报错中止)    │

│ 4. doctor — 迁移改写(用户主动)                              │
│    → 用户跑 doctor 修复                                     │
│    → doctor 用共享迁移规则把 retired key 改写为新形态        │
│    → 改写后运行时拿到纯净的当前形态                         │
└──────────────────────────────────────────────────────────────┘
```

## 关键设计约束

### 1. 物化在先,校验在后

- **为什么**:校验未物化的原始配置会因默认值缺失而报假错;运行时真正用的是物化后的形态
- **怎么做**:物化器先填默认值、归一化路径,校验器再对物化结果做合约校验
- **影响**:校验看到的是"运行时真正会用的形态",报错反映真实问题

### 2. 合并补丁防原型链污染

- **为什么**:配置是用户可控的外部输入,若允许 `__proto__`/`constructor` 等 key,会触发原型链污染攻击
- **怎么做**:合并补丁在应用前阻断危险 key;克隆用安全方式
- **影响**:即使用户配置里写了危险 key,也不会污染对象原型

### 3. 遗留检测不改写,只报告

- **为什么**:运行时改写旧 key 会与"无静默兼容"原则冲突;用户不知道发生了什么
- **怎么做**:遗留检测收集问题清单,运行时只读最新形态;改写只在 doctor 迁移代码里
- **影响**:用户须主动跑 doctor 完成迁移;retired key 保持 retired

### 4. 字段标签是闭集

- **为什么**:标签用于 UI 筛选分组,自由字符串会让筛选器失效、分组不可预测
- **怎么做**:标签用稳定词汇表(security/auth/network/access...);有优先级排序
- **影响**:新增标签须审视词汇表;UI 可稳定分组展示

### 5. 变更基线可选 runtime 或 source

- **为什么**:有些变更是给运行时形态用的(含默认值),有些是写回原始用户配置(不含默认值);混淆会把默认值污染进用户文件
- **怎么做**:变更器显式选定基线形态;写入时还原成 source 形态落盘
- **影响**:用户文件不会被系统填的默认值污染,保持精简

### 6. 校验失败必须中止而非放行

- **为什么**:静默放行非法配置会让运行时行为不可预测,且用户以为配置生效了
- **怎么做**:校验失败抛含字段路径与修复建议的错误;Gateway 启动中止
- **影响**:用户能立即定位问题;不会带病启动

## 设计观察

### 为什么帮助文本与 Schema 同源

```
错误设计:
   UI 代码里硬编码字段帮助
   文档里手写另一份字段说明
   Schema 里只有结构没有描述
   → 三处漂移,改字段时只改一处 → 用户看到过期帮助

正确设计:
   字段帮助按 dot-path 集中定义
   → 基础 Schema 生成器递归合并到 Schema 树
   → UI 与文档都从同一份 Schema 读取帮助
   → 改字段帮助只改一处,全局生效
```

### 为什么合并补丁用 null 表删除

```
场景:用户想删除某配置字段

错误做法:用 undefined 或空字符串表删除
   → 与"字段缺失"无法区分
   → 与"用户显式设为空"无法区分

正确做法:RFC 7396 风格,null 表删除
   → null = 显式删除该字段
   → 缺失 = 不动该字段
   → 语义清晰,补丁可序列化、可审计
```
