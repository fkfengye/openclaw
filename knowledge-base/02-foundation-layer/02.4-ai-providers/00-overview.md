# 00 — AI Provider 抽象层总览

> 读完本章你将理解:OpenClaw 如何把 LLM 厂商抽象成可替换的 Provider,核心运行时为何不绑定任何特定厂商,以及 Provider 抽象层由哪些组件构成、组件之间如何协作。

## 一句话定位

AI Provider 抽象层是 OpenClaw 与外部 LLM 服务之间的隔离带:
- 一套契约层定义"模型 / 消息 / 流 / 工具"的统一形状
- 一组适配器把各厂商 SDK 翻译成这套契约
- 传输层接管流式返回与代理 / TLS 策略
- 切换厂商只换 Provider,Agent Runner 不变

## 组件清单

Provider 抽象层由 4 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **Provider 核心契约层** | 定义模型、消息、工具、流的统一类型与校验 | 纯类型,不依赖任何厂商 SDK;可被外部复用 |
| **Provider 注册与运行时** | API 注册表、主机策略、环境密钥、会话资源、流式辅助 | 注册表惰性加载;主机策略由嵌入应用注入 |
| **Provider 实现** | 各厂商 SDK 适配器,翻译为统一契约 | 每个适配器只翻译不引入新契约;惰性注册 |
| **传输层** | 流式返回解析、fetch 守卫、代理 / TLS / 重试 | 传输层接管网络策略;Provider 实现不直接 fetch |
| **工具与内部** | 溢出控制、缓存稳定性、错误归一、OAuth、内部适配 | 横向辅助;确定性排序以保缓存友好 |

### 为什么分四层而非一层

```
错误设计(单层):
   Agent Runner ──直接调用──► OpenAI SDK
   → 切换厂商要改 Agent Runner
   → 网络策略散落在各处
   → 流式解析逻辑重复

正确设计(四层):
   Agent Runner
        │
        ▼
   核心契约层   ← 类型统一,不依赖厂商
        │
        ▼
   注册运行时   ← 惰性注册,可替换
        │
        ▼
   Provider 实现 ← 各厂商翻译
        │
        ▼
   传输层       ← 网络 / 流式策略集中
        │
        ▼
   外部 LLM
```

## 协作流程

### 一次 LLM 调用的完整旅程

下面追踪 Agent Runner 发起一次 LLM 请求,从注册表查找适配器到流式返回的全过程。

```
Agent Runner 准备发起 LLM 调用
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 查找适配器                                                 │
│    → API 注册表按模型的 API 类型查找已注册适配器              │
│    → 适配器惰性加载(首次使用时才 import 厂商 SDK)           │
│    → 返回流式函数(同步返回,异步加载)                       │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 解析密钥与策略                                             │
│    → 环境密钥解析器从环境变量 / 配置文件读取 API Key          │
│    → 主机策略端口注入 fetch 守卫(密钥脱敏 / 端点校验)       │
│    → 会话资源追踪器绑定当前会话的资源上下文                   │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 传输路由                                                   │
│    → 传输路由分发器按 API 类型选择对应传输流                  │
│    • Anthropic 消息 → Anthropic 传输流                        │
│    • OpenAI 补全   → OpenAI 补全传输流                        │
│    • OpenAI 响应   → OpenAI 响应传输流                        │
│    • Azure OpenAI  → Azure 响应传输流                         │
│    → 不在路由表中的 API 走 Provider 自有 fetch                │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 请求构造与发送                                             │
│    → Provider 实现把统一消息翻译成厂商请求体                  │
│    → 传输层注入 fetch 守卫 / 代理 / TLS 策略                  │
│    → 请求发出(带超时与首事件守卫)                           │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 5. 流式接收与事件翻译                                         │
│    → 传输层解析 SSE / chunked 原始字节流                      │
│    → 字节守卫防止畸形分片导致解析错误                         │
│    → Provider 实现把厂商事件翻译成统一事件                    │
│    → 统一事件推入事件流管道                                   │
│                                                              │
│    循环直到流结束:                                           │
│    ├─ 文本 chunk → 累积到回复                                │
│    ├─ 工具调用 → 翻译为统一工具事件                          │
│    ├─ 用量信息 → 翻译为统一用量事件                          │
│    └─ 结束信号 → 翻译为统一终态                              │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 6. 错误处理与归一                                             │
│    → 若发生错误:Provider 错误归一器把厂商错误翻译为统一格式  │
│    → TLS 证书错误特殊处理(区分可恢复 / 不可恢复)            │
│    → 溢出控制器处理 token 超限场景                           │
│    → 错误事件推入事件流管道                                  │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
                  Agent Runner 收到统一事件流
                  (后续交由终态归一化器处理)
```

## 关键设计约束

### 1. 核心契约层不依赖任何厂商 SDK

- **为什么**:契约层是所有 Provider 实现的共同基础;若依赖厂商 SDK,则外部复用者被迫安装全部 SDK
- **怎么做**:契约层只定义类型与接口,不引入任何厂商 SDK 依赖
- **影响**:契约层可独立发布为单独包,外部项目可只引用类型而不引入厂商依赖

### 2. Provider 实现惰性注册与加载

- **为什么**:一次性加载所有厂商 SDK 会拖慢启动、占用内存;大多数部署只用一两个厂商
- **怎么做**:注册时只记录加载器,首次调用才触发 import;加载结果缓存
- **影响**:首次调用有 import 延迟,但同步返回事件流(异步加载在后台),调用方无感知

### 3. 传输层接管网络策略

- **为什么**:代理 / TLS / 重试 / 密钥脱敏等策略对每个厂商都一样,散落在各 Provider 实现中会重复且不一致
- **怎么做**:传输层统一注入 fetch 守卫;Provider 实现不直接 fetch,而是通过传输层发请求
- **影响**:切换网络策略只改传输层,所有 Provider 实现同时生效

### 4. 确定性排序保缓存友好

- **为什么**:prompt cache 命中要求相同输入产生相同 cache key;若工具表 / 消息顺序不确定,cache 永远 miss
- **怎么做**:工具表、消息、注册表等在进入模型请求前做确定性排序;缓存稳定性辅助器校验排序不变
- **影响**:相同会话历史 + 相同工具表产生相同请求体,cache 命中率提升

### 5. OAuth 流程用于 ChatGPT / Copilot 类 Provider

- **为什么**:部分厂商(如 ChatGPT 桌面版、GitHub Copilot)不走标准 API Key,而是走 OAuth 令牌交换
- **怎么做**:OAuth 模块处理令牌获取与刷新;Provider 实现在请求前注入 OAuth 头部
- **影响**:这些 Provider 的认证流程独立于标准 API Key 路径

### 6. TLS 证书错误需特殊处理

- **为什么**:企业内网 / 代理 / 本地模型常使用自签证书;直接抛错会导致这些场景不可用
- **怎么做**:TLS 错误归一器区分"证书过期 / 证书不匹配 / 未知 CA"等类型,给出可操作的诊断信息
- **影响**:用户能区分"网络问题"与"证书问题",便于排查

## 设计观察

### 为什么 Provider 实现不直接发 fetch

```
错误设计:
   Provider 实现 ──直接 fetch──► 外部 LLM
   → 每个厂商各自处理代理 / TLS / 密钥脱敏
   → 策略不一致,维护成本高
   → 无法统一注入 fetch 守卫

正确设计:
   Provider 实现 ──► 传输层 ──► 外部 LLM
                         ▲
                         │
                    主机策略端口
                    (fetch 守卫注入)
   → 代理 / TLS / 脱敏策略集中
   → Provider 实现只管翻译,不管网络
```

### 为什么契约层独立成包

```
单包设计:
   AI 包同时包含类型与厂商 SDK
   → 外部项目只想用类型 → 被迫安装全部 SDK
   → 包体积大,安装慢

分包设计:
   核心契约包  ← 纯类型与契约(零厂商依赖)
   AI 适配包   ← 厂商适配器(依赖各 SDK)
   → 外部项目可只引用核心契约包获得类型
   → 包职责清晰,边界明确
```

### 为什么用注册表而非硬编码分支

```
硬编码设计:
   核心代码里按 API 类型分支判断
   → 新增厂商要改核心代码
   → 插件无法注册自有 Provider

注册表设计:
   核心只管向注册表查找与调用
   → 新增厂商 = 注册新适配器,核心不变
   → 插件可注册自有 Provider 覆盖内置
   → 来源标记区分内置与插件,可批量卸载
```
