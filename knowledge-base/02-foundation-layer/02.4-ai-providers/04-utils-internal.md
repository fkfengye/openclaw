# 04 — 工具与内部

> 读完本章你将理解:横向辅助层由哪些模块组成,prompt cache 稳定性为何需要确定性排序,OAuth 如何处理 ChatGPT 令牌,以及内部适配器层为何存在。

## 一句话定位

工具与内部层是抽象层的横向辅助:
- 工具模块为所有层提供横切能力(溢出控制、缓存稳定、错误归一、字节守卫)
- OAuth 模块处理非标准认证(ChatGPT 令牌交换)
- TLS 错误归一器把证书问题翻译为可操作诊断
- 内部适配器层封装厂商 SDK 的共享细节

## 组件清单

工具与内部层由 3 类共 16 个模块协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **溢出控制器** | 处理 token 超限场景,截断或压缩上下文 | 保系统提示完整;优先保留最近消息 |
| **缓存稳定性校验器** | 校验请求体确定性排序,保 cache 友好 | 工具表 / 消息 / 注册表确定性排序 |
| **Provider 错误归一器** | 把各厂商错误翻译为统一错误格式 | 保留原始诊断;区分可重试 / 不可重试 |
| **流式字节守卫** | 防止畸形分片导致流式解析错误 | 缓冲不完整分片;确保完整事件边界 |
| **系统提示缓存边界** | 标记系统提示的缓存边界,保 cache 命中 | 边界标记确定性注入;不跨消息移动 |
| **TLS 证书错误归一器** | 把 TLS 证书错误分类为可操作诊断 | 区分过期 / 不匹配 / 未知 CA / 自签 |
| **首事件超时守卫** | 连接后多久没收到第一个事件则超时 | 独立于总超时;区分"连不上"与"不响应" |
| **延迟事件缓冲器** | 缓冲乱序或延迟到达的事件 | 保事件顺序;背压安全 |
| **推理标签分区器** | 把推理标签文本分区为结构化片段 | 模型推理输出解析 |
| **助手文本相位器** | 处理助手消息的文本相位 | 流式文本累积 |
| **诊断模块** | 结构化诊断信息输出 | 脱敏;可观测 |
| **OAuth 令牌** | ChatGPT 的 JWT 令牌获取与交换 | 非标准认证;独立于 API Key 路径 |
| **Anthropic 内部适配器** | 桥接 Anthropic SDK 与统一契约 | SDK 版本差异吸收 |
| **OpenAI 内部适配器** | 桥接 OpenAI SDK 与统一契约 | SDK 版本差异吸收 |
| **共享内部模块** | Anthropic 与 OpenAI 内部适配器的公共逻辑 | 避免重复 |
| **重试模块(延迟与休眠)** | 解析重试后延迟;执行重试休眠 | 退避策略;可取消 |

### 缓存稳定性与确定性排序的关系

```
   ┌──────────────────────────────────────────────────────────┐
   │  缓存稳定性校验器                                        │
   │                                                          │
   │  校验对象:                                              │
   │  ┌────────────────┐  ┌────────────────┐                │
   │  │ 工具表          │  │ 消息列表       │                │
   │  │ (排序确定性)    │  │ (顺序确定性)   │                │
   │  └────────────────┘  └────────────────┘                │
   │  ┌────────────────┐  ┌────────────────┐                │
   │  │ 注册表          │  │ 系统提示       │                │
   │  │ (遍历确定性)    │  │ (边界确定性)   │                │
   │  └────────────────┘  └────────────────┘                │
   │                                                          │
   │  校验目的:                                              │
   │  → 相同输入产生相同请求体                                │
   │  → 相同请求体 → cache 命中                              │
   │  → cache 命中 → 减少延迟与 token 消耗                  │
   └──────────────────────────────────────────────────────────┘

   ┌──────────────────────────────────────────────────────────┐
   │  系统提示缓存边界                                        │
   │                                                          │
   │  职责:                                                  │
   │  → 标记系统提示的缓存边界位置                            │
   │  → 边界标记确定性注入(不因调用次数变化)               │
   │  → 与缓存稳定性校验器配合                                │
   │                                                          │
   │  为什么需要:                                             │
   │  → 系统提示通常很长且不变                                │
   │  → 正确的边界标记让厂商缓存系统提示                      │
   │  → 边界位置不确定 → cache 永远 miss                     │
   └──────────────────────────────────────────────────────────┘
```

### OAuth 令牌与标准 API Key 的区别

```
   ┌──────────────────────────────────────────────────────┐
   │  标准 API Key 路径                                   │
   │                                                      │
   │  环境密钥解析器 → API Key → 请求头部注入             │
   │  → 每次请求用同一个 Key                              │
   │  → Key 不过期(除非手动轮换)                       │
   └──────────────────────────────────────────────────────┘

   ┌──────────────────────────────────────────────────────┐
   │  OAuth 令牌路径(ChatGPT 桌面版)                    │
   │                                                      │
   │  OAuth 模块 → JWT 令牌交换 → 短期访问令牌            │
   │  → 令牌有过期时间                                    │
   │  → 过期后需要重新交换                                │
   │  → 令牌交换走独立的认证流程                          │
   │  → 不经过环境密钥解析器                              │
   │                                                      │
   │  为什么独立:                                         │
   │  • ChatGPT 桌面版不走标准 API Key                   │
   │  • 需要本地令牌交换(用户已登录的会话)              │
   │  • 令牌刷新逻辑与标准 Key 完全不同                   │
   └──────────────────────────────────────────────────────┘
```

## 协作流程

### token 溢出时的处理流程

```
LLM 返回 token 超限错误
         │
         ▼
┌──────────────────────────────────────────────────────┐
│ 1. 错误归一                                           │
│    → Provider 错误归一器把厂商错误翻译为统一格式     │
│    → 识别为"token 超限"类型                          │
│    → 传递给溢出控制器                                │
└────────────────────────────┬─────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────┐
│ 2. 上下文截断                                         │
│    → 溢出控制器评估当前上下文长度                    │
│    → 截断策略:                                       │
│      • 保留系统提示(完整)                          │
│      • 保留最近 N 轮对话                            │
│      • 丢弃最早的对话消息                           │
│      • 保留工具调用结果(除非超限)                  │
└────────────────────────────┬─────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────┐
│ 3. 重试请求                                           │
│    → 用截断后的上下文重新构造请求                    │
│    → 重试模块执行退避休眠(避免立即重试)            │
│    → 重新发送请求                                    │
└────────────────────────────┬─────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────┐
│ 4. 结果处理                                           │
│    → 成功 → 流式返回                                 │
│    → 仍然超限 → 进一步截断或报错                     │
│    → 其他错误 → 交给错误归一器                       │
└──────────────────────────────────────────────────────┘
```

## 关键设计约束

### 1. 确定性排序保缓存友好

- **为什么**:prompt cache 命中要求相同输入产生相同 cache key;工具表 / 消息 / 注册表顺序不确定会导致 cache 永远 miss
- **怎么做**:缓存稳定性校验器校验请求体确定性;Map / Set / 注册表在进入模型请求前做确定性排序;系统提示缓存边界确定性注入
- **影响**:相同会话历史 + 相同工具表产生相同请求体;cache 命中率提升;减少 token 消耗与延迟

### 2. TLS 错误需分类诊断

- **为什么**:企业内网 / 代理 / 本地模型常使用自签证书;直接抛"TLS 错误"无法区分原因,用户无法排查
- **怎么做**:TLS 错误归一器解析原始错误,匹配已知证书错误模式,生成分类诊断信息(错误类型 + 端点 + 建议操作)
- **影响**:用户能区分"证书过期"(检查系统时间)与"未知 CA"(安装证书);减少排查时间

### 3. OAuth 独立于标准 API Key 路径

- **为什么**:ChatGPT 桌面版 / GitHub Copilot 不走标准 API Key;令牌有过期时间,需要刷新;混入标准路径会污染密钥解析器
- **怎么做**:OAuth 模块独立处理令牌获取与交换;不经过环境密钥解析器;令牌缓存与自动刷新
- **影响**:标准 API Key 路径保持简洁;OAuth 用户获得透明的令牌管理;令牌刷新失败有明确错误

### 4. 溢出控制保系统提示完整

- **为什么**:系统提示包含 agent 的核心指令与工具定义;截断系统提示会导致 agent 行为异常
- **怎么做**:溢出控制器截断时优先保留系统提示;其次保留最近对话;最早消息优先丢弃;工具调用结果尽量保留
- **影响**:token 超限时 agent 行为不崩溃;对话历史逐步缩短而非丢失关键上下文

### 5. 内部适配器层避免 SDK 桥接重复

- **为什么**:Anthropic / OpenAI 适配器都需要桥接各自 SDK;若各自实现桥接逻辑,SDK 版本变更要改多处
- **怎么做**:SDK 桥接逻辑提取到内部适配器层;共享内部模块提供公共逻辑;重试模块(延迟解析 + 休眠)可被传输层与适配器共用
- **影响**:SDK 版本变更只改内部适配器;重试逻辑单一来源;适配器代码更简洁

### 6. 流式字节守卫防止畸形分片

- **为什么**:流式传输中一个逻辑事件可能跨多个网络分片;直接按行解析遇到半行会报错
- **怎么做**:字节守卫缓冲不完整分片;确保解析器只处理完整的事件边界;与首事件超时守卫配合
- **影响**:网络抖动不导致解析错误;流式接收更健壮;减少假错误

## 设计观察

### 为什么缓存稳定性需要校验器

```
无校验器设计:
   请求体构造时排序,但不校验
   → 某处遗漏排序 → cache miss
   → 开发者不知道哪里漏了
   → cache 命中率低,难以排查

有校验器设计:
   缓存稳定性校验器校验请求体确定性
   → 发现非确定性排序 → 发出警告
   → 开发者立即知道哪里漏了
   → cache 命中率有保障
   → 校验器在开发 / 测试时生效,生产可关闭
```

### 为什么重试逻辑提取到内部层

```
分散设计:
   每个适配器自己实现重试
   → 重试策略不一致
   → Retry-After 头部解析重复
   → 退避休眠逻辑重复

集中设计:
   重试延迟解析器 + 重试休眠器在内部层
   → 传输层与适配器共用
   → 重试策略统一
   → Retry-After 解析单一来源
   → 退避休眠可取消(支持用户取消)
```

### 为什么溢出控制器不直接丢弃系统提示

```
错误截断策略:
   超限时按比例截断所有消息
   → 系统提示被截断
   → agent 核心指令丢失
   → 工具定义丢失
   → agent 行为异常(不知道有哪些工具,不知道指令)

正确截断策略:
   保留系统提示(完整)
   保留最近 N 轮对话
   丢弃最早对话
   → agent 核心指令不丢
   → 工具定义不丢
   → 对话历史缩短但 agent 行为正常
   → 用户体验:agent "忘记"早期对话但保持能力
```
