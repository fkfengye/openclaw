# 02 — 会话管理器

> 读完本章你将理解:会话树如何以 SQLite transcript 身份为根组织,分支/编解码/条目/持久化如何拆分到 8 个聚焦模块,以及为什么门面只暴露当前规范会话版本。

## 一句话定位

会话管理器是会话历史的**持久化与树结构层**:
- 以 SQLite transcript 身份为根,管理会话树的分支、条目、编解码与持久化
- 门面模式:对外只暴露当前规范会话版本,内部按职责拆成 7 个聚焦模块
- 老旧/不透明条目只在加载时归一化,运行时不读旧 shape

## 组件清单

会话管理器由门面 + 4 层继承 + 3 个内部模块组成:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **会话管理器门面** | 对外唯一入口,重导出当前规范类型与版本 | 只暴露当前会话版本,不暴露旧 shape |
| **分支层** | 分支路径收集,fork,标签/重置/模型变更写入 | fork 创建新文件,导航不创建 |
| **条目层** | 条目追加/替换/读取,提示发布条目合并 | 写入前归一化为规范形状 |
| **持久化层** | 追加选项,文件条目,合并结果 | 与具体存储后端解耦 |
| **核心存储层** | 持久化目标抽象,会话树节点与叶子控制 | 持久化目标可替换 |
| **编解码层** | 条目解析,形状归一化,迁移 | 不透明条目解析为父链结构 |
| **标识层** | 会话 ID 与条目 ID 生成 | ID 唯一性保证 |
| **类型层** | 条目类型,树节点,头部定义 | 区分消息/压缩/标签/重置/模型变更等条目 |

## 关联关系

### 门面与内部模块的边界

```
   ┌──────────────────────────────────────────┐
   │  会话管理器门面(对外)                  │
   │                                          │
   │  • 只重导出当前规范类型                  │
   │  • 只重导出当前会话版本常量              │
   │  • 调用方只认门面,不认内部模块          │
   └──────────────────┬───────────────────────┘
                      │
                      │ 内部委托
                      ▼
   ┌──────────────────────────────────────────┐
   │  内部模块(不对外)                      │
   │                                          │
   │  • 编解码:解析与归一化                  │
   │  • 标识:ID 生成                         │
   │  • 类型:内部条目形状                    │
   └──────────────────────────────────────────┘

   反例:调用方直接 import 内部模块
        → 内部模块变更直接影响调用方
        → 门面失去保护作用
```

### 会话树的父子链结构

```
   会话树(transcript 身份为根)
        │
        ├── 条目 A(消息)
        │     │
        │     └── 子条目 B(消息)── 父链指向 A
        │           │
        │           └── 子条目 C(压缩)── 父链指向 B
        │
        ├── 条目 D(消息,与 A 平级)
        │
        └── 不透明条目(旧格式)
              │
              └── 加载时解析为父链结构
                 (运行时不读旧 shape)

   规则:
   • 每个条目记录父条目 ID,形成树
   • 分支 = 从叶子回溯到根的路径
   • fork = 复制路径到新文件
   • 导航 = 同文件内跳到另一叶子
```

## 协作流程

### 加载一个分支会话的完整过程

下面追踪从会话管理器加载一个分支会话到上下文可用的全过程。

```
调用方请求加载分支会话(指定叶子 ID)
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 门面接收请求                                               │
│    → 委托给分支层                                            │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 分支层收集分支路径                                        │
│    → 从叶子 ID 回溯到根                                     │
│    → 收集路径上的条目与不透明条目                           │
│    → 记录已用 ID 集合(防环)                                │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 编解码层解析条目                                          │
│    → 规范条目:直接解析                                     │
│    → 不透明条目:解析为父链结构(旧格式归一化)              │
│    → 投影为当前规范形状                                     │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 核心存储层组装会话上下文                                  │
│    → 把条目序列组装成会话上下文                             │
│    → 取最新压缩条目(如有)作为上下文起点                   │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 5. 返回会话上下文给调用方                                    │
│    → 调用方用于构建 prompt                                  │
└──────────────────────────────────────────────────────────────┘
```

### fork 与导航的区别

为什么 fork 创建新文件而导航不创建?用反例说明。

```
场景:用户想尝试两种不同方案,从同一起点分叉

fork(正确):
   起点 ──fork──► 新会话文件(复制路径)
                    │
                    └── 在新文件里继续
   → 两套方案各自独立文件,互不干扰
   → 可随时回到任一文件

导航(错误用于分叉):
   起点 ──导航──► 跳到同文件的另一节点
   → 不产生新文件,只是视角切换
   → 无法保留两套方案

   结论:fork = 新建,导航 = 切换;职责不可混用
```

## 关键设计约束

### 1. 门面只暴露当前规范会话版本

- **为什么**:防止调用方依赖旧 shape,迁移后留下兼容债务
- **怎么做**:门面只重导出当前会话版本常量与规范类型;旧 shape 只在编解码层归一化
- **影响**:调用方只认门面,版本升级时只改编解码层

### 2. 不透明条目加载时归一化

- **为什么**:旧格式条目不能在运行时反复读,否则每次都要处理兼容
- **怎么做**:加载时编解码层把不透明条目解析为父链结构,投影为规范形状
- **影响**:运行时只处理规范形状,无旧 shape 分支

### 3. 写入前归一化为规范形状

- **为什么**:持久化的条目必须是当前规范形状,防止旧格式扩散
- **怎么做**:条目追加/替换前先投影为规范形状再写入
- **影响**:存储里只有规范形状,加载时无需额外迁移

### 4. 分支路径收集防环

- **为什么**:会话树可能出现循环引用(异常状态),回溯会死循环
- **怎么做**:收集分支路径时记录已用 ID 集合,遇到重复即停
- **影响**:异常状态下不卡死,优雅降级

### 5. 持久化目标可替换

- **为什么**:测试时需要替换存储后端,不依赖真实 SQLite
- **怎么做**:核心存储层抽象出持久化目标接口,测试可注入 stub
- **影响**:会话管理器可独立测试,无需真实数据库

## 设计观察

### 为什么用门面 + 内部模块拆分而非单一大类

```
单一大类:
   • 所有逻辑塞进一个类 → 数千行,难维护
   • 编解码/标识/持久化逻辑混在一起 → 职责模糊
   • 内部细节被迫对外暴露 → 调用方耦合内部

门面 + 内部模块(当前):
   • 门面只暴露规范类型,保护内部
   • 编解码/标识/持久化各自聚焦,可独立测试
   • 继承栈(分支→条目→核心)按"行为特化"分层
   • 内部模块按"无状态工具"组织
   → 职责清晰,边界明确
```

### 为什么编解码层要投影规范形状

```
错误设计:
   运行时直接读存储里的任意 shape
   → 每个 reader 都要处理 N 种历史格式
   → 兼容代码散落各处

正确设计:
   加载时编解码层统一投影为规范形状
   → 运行时只认规范形状
   → 兼容代码集中在编解码层一处
   → 符合"核心运行时只消费当前规范形状"的硬约束
```
