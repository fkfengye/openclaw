# 05 — 压缩与扩展

> 读完本章你将理解:长会话如何被压缩(摘要+裁剪),分支切换时如何总结被放弃的分支,以及会话级 TS 扩展如何被 jiti 动态加载并管理生命周期。

## 一句话定位

压缩与扩展层是会话的**容量治理与可扩展性层**:
- 上下文压缩桥接共享 agent-core,本地保留历史抛错式 API,agent-core 返回 Result
- 分支摘要把会话管理器的分支遍历留在本地,摘要生成委托 agent-core
- 扩展加载器用 jiti 动态加载 TS 扩展,静态依赖由 Bun 打包进二进制;扩展运行器管理生命周期

## 组件清单

压缩与扩展层由 2 个子层、6 个组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **上下文压缩桥接** | 压缩判定/摘要生成/历史裁剪,Result 拆包 | 本地保留抛错式 API,委托 agent-core |
| **分支摘要桥接** | 分支遍历/摘要生成/文件操作,Result 拆包 | 分支遍历留本地,摘要生成委托 agent-core |
| **扩展加载器** | jiti 加载 TS 扩展,虚拟模块,别名映射 | 静态依赖由 Bun 打包,虚拟模块沙箱化 |
| **扩展运行器** | 扩展生命周期管理,事件分发,错误监听 | 工具调用/结果拦截由 agent-core Hook 统一处理 |
| **工具包装器** | 把扩展工具包装为 agent 工具 | 只注入运行器上下文,不实现拦截语义 |
| **扩展类型** | 扩展与事件类型定义 | 类型契约稳定 |

## 关联关系

### 压缩桥接的 API 转换

```
   ┌─────────────────────────────────────────────┐
   │  会话生命周期层(本地调用方)               │
   │                                             │
   │  • 期望历史抛错式 API(失败抛异常)         │
   └────────────────────┬────────────────────────┘
                        │ 调用
                        ▼
   ┌─────────────────────────────────────────────┐
   │  压缩桥接层                                 │
   │                                             │
   │  ① 接收本地调用(抛错式)                   │
   │  ② 转发到 agent-core                        │
   │  ③ 接收 Result(成功/失败)                 │
   │  ④ 拆包:成功→返回值,失败→抛异常          │
   └────────────────────┬────────────────────────┘
                        │ 委托
                        ▼
   ┌─────────────────────────────────────────────┐
   │  共享 agent-core                            │
   │                                             │
   │  • 压缩算法(裁剪点查找/摘要生成/序列化)  │
   │  • 返回 Result,不抛错                      │
   └─────────────────────────────────────────────┘

   反例:本地重写压缩算法
        → 算法逻辑重复,与 agent-core 漂移
        → 维护两套裁剪规则
```

### 分支摘要的职责切分

```
   ┌─────────────────────────────────────────────┐
   │  会话管理器(本地)                         │
   │                                             │
   │  • 分支遍历(从叶子回溯到根)               │
   │  • 收集路径条目                             │
   │  • 找公共祖先                               │
   └────────────────────┬────────────────────────┘
                        │ 传递收集的条目
                        ▼
   ┌─────────────────────────────────────────────┐
   │  分支摘要桥接                               │
   │                                             │
   │  • 接收本地收集的分支条目                   │
   │  • 委托 agent-core 生成摘要                 │
   │  • 拆包 Result                              │
   └─────────────────────────────────────────────┘

   为什么要切分?
   • 分支遍历依赖会话管理器的树结构知识 → 必须留本地
   • 摘要生成是通用算法 → 委托 agent-core 避免重复
```

### 扩展加载器的虚拟模块沙箱

```
   ┌─────────────────────────────────────────────┐
   │  扩展加载器(jiti)                         │
   │                                             │
   │  ① 静态 import 核心包(typebox/llm/sdk)    │
   │     → 必须静态,Bun 才能打包进二进制        │
   │  ② 虚拟模块映射                             │
   │     → 把静态 import 的包暴露给扩展          │
   │     → 扩展 import "typebox" 实际拿静态包    │
   │  ③ 别名映射                                 │
   │     → 核心 SDK 别名解析                     │
   │  ④ jiti 动态加载扩展 TS 文件                │
   └────────────────────┬────────────────────────┘
                        │
                        ▼
   ┌─────────────────────────────────────────────┐
   │  扩展模块(用户/第三方 TS)                 │
   │                                             │
   │  • 运行时加载,无需重编译核心               │
   │  • 通过虚拟模块访问核心包                   │
   │  • 不能直接 import 核心内部                 │
   └─────────────────────────────────────────────┘
```

### 一次上下文压缩的完整过程

下面追踪会话上下文超阈值到压缩完成的全过程。

```
会话检视层估算上下文用量 → 超阈值
         │
         ▼

│    → 触发类型:手动 / 阈值 / 溢出                           │
│    → 准备压缩工作                                            │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 压缩桥接判定                                              │
│    → 是否需要压缩?(委托 agent-core 判定)                  │
│    → 不需要?跳过                                           │
│    → 需要?继续                                            │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 压缩桥接准备                                              │
│    → 找裁剪点(委托 agent-core)                            │
│    → 找 turn 起始索引                                       │
│    → 估算上下文 token                                       │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 压缩桥接生成摘要                                          │
│    → 序列化对话(委托 agent-core)                          │

│    → 拆包 Result:成功→摘要,失败→抛异常                   │

```

## 关键设计约束

### 1. 压缩桥接保留抛错式 API

- **为什么**:本地调用方期望历史抛错式 API,改造成本高;agent-core 用 Result 更安全
- **怎么做**:桥接层接收本地调用,转发 agent-core,拆包 Result:成功返回值,失败抛异常
- **影响**:调用方无需改造,agent-core 的 Result 语义被隔离在桥接层

### 2. 分支遍历留本地,摘要生成委托

- **为什么**:分支遍历依赖会话管理器的树结构知识,agent-core 不应感知;摘要生成是通用算法,重复实现无意义
- **怎么做**:会话管理器收集分支条目,桥接层把条目传给 agent-core 生成摘要
- **影响**:树结构与摘要算法解耦,各自演进

### 3. 扩展静态依赖必须静态 import

- **为什么**:Bun 打包二进制时,只有静态 import 的包才会被打包;动态 import 不会
- **怎么做**:扩展可能用的核心包(typebox/llm/sdk)在加载器顶部静态 import,再通过虚拟模块暴露给扩展
- **影响**:扩展运行时 import 这些包实际拿到打包进二进制的版本,无需另装

### 4. 工具拦截由 agent-core Hook 统一处理

- **为什么**:避免扩展层与 agent-core 两套拦截逻辑不一致
- **怎么做**:工具包装器只注入运行器上下文,工具调用/结果拦截由 agent-core Hook 统一处理
- **影响**:扩展层只负责"把扩展工具接入",不负责拦截语义

### 5. 虚拟模块沙箱化核心包

- **为什么**:扩展不应直接 import 核心内部,要走 SDK 边界
- **怎么做**:加载器通过虚拟模块把核心包暴露给扩展,扩展 import 别名实际拿到映射的包
- **影响**:扩展不能绕过 SDK 边界访问核心内部,符合插件边界约束

## 设计观察

### 为什么压缩委托 agent-core 而非本地实现

```
本地实现(错误):
   会话层 ──自己实现──► 裁剪点查找 / 摘要生成 / 序列化
   → 算法逻辑重复,与 agent-core 漂移
   → 两套裁剪规则,行为可能不一致
   → 维护成本翻倍

委托 agent-core(正确):
   会话层 ──► 压缩桥接 ──► agent-core(算法)
              (只做 API 转换)
   → 单一算法实现,行为一致
   → 会话层只管 API 形状转换
```

### 为什么扩展加载用 jiti 而非原生 require

```
原生 require(错误):
   • 只能加载已编译 JS,不能加载 TS
   • 扩展必须预编译 → 用户体验差
   • 缓存策略与核心混在一起

jiti(正确):
   • 运行时加载 TS,无需预编译
   • 虚拟模块 + 别名映射 → 沙箱化
   • 与 Bun 打包协同(静态 import 打包,动态 jiti 加载扩展)
   → 用户写 TS 扩展即可运行,无需构建步骤
```
