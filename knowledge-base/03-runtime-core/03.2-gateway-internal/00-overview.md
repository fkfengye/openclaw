# 00 — Gateway 内部编排总览

> 这是 Gateway 内部编排目录的入口。读完本章你将理解:Gateway 在接入面之后由哪些内部组件构成、它们如何协作把外部连接变成可处理的对话、配置与凭据如何在运行时流动。

## 一句话定位

Gateway 内部编排是接入面与 Agent 运行时之间的"操作系统":
- 启动分阶段编排,认证面归一为单一结果,客户端连接生命周期被严格管理
- 对话与聊天显示以投影而非状态机方式管理,所有 UI 后端能力以 HTTP 子面形式提供
- 凭据规划、渠道健康、定时流、执行审批构成横向监控与授权面

## 组件清单

Gateway 内部编排由 6 类组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **启动与生命周期** | 5 阶段启动编排、回声守卫、客户端启动就绪检查、配置热重载 | 阶段顺序固定;热重载只支持最新 shape |
| **认证内部** | 7 种认证方法归一为单一结果、限速、模式策略、安装策略、表面解析、令牌解析 | 认证结果不可旁路;表面解析决定可见能力 |
| **客户端与对话** | 连接生命周期管理、Turn 编排、对话列表/读取/发送、错误归一 | 同会话串行;错误统一归一化 |
| **聊天显示投影** | 事件流投影为可见消息、附件处理、中止、排队 Turn、输入/输出清洗 | 投影只读不可写回状态;清洗双向 |
| **Control UI 后端** | CSP 策略、路由、Session PRS、GitHub 预览、插件 Tab | CSP 严格;插件 Tab 沙箱隔离 |
| **凭据与监控** | 凭据规划、设备认证、渠道健康监控、定时流、执行审批 | 凭据不落日志;审批需显式授权 |

### 反例:不该把投影逻辑混入对话面

```
错误设计:
   对话面 ──直接构造可见消息──► UI / 渠道
   → 对话面耦合显示规则
   → 切换显示风格要改对话面
   → 渠道特定清洗规则污染对话内核

正确设计:
   对话面 ──产出事件流──► 聊天显示投影 ──► UI / 渠道
                         ↑
                    双向清洗 + 附件 + 中止
   → 对话面只关心 Turn 语义
   → 投影面独立演进显示规则
```

## 关键设计约束

### 1. 启动分阶段且顺序固定

- **为什么**:每阶段职责独立,便于定位启动失败点
- **怎么做**:5 阶段严格串行,前一阶段失败不进下一阶段
- **影响**:插件加载在最后,核心运行时先就绪

### 2. 认证结果归一不可旁路

- **为什么**:7 种认证方法若各自返回不同结构,下游无法统一处理
- **怎么做**:所有认证方法产出同一形状的认证结果,含可见能力集
- **影响**:下游组件只认归一结果,不再关心是哪种方法认证的

### 3. 投影只读不可写回状态

- **为什么**:投影是事件流的派生物,写回状态会破坏事件溯源
- **怎么做**:投影面只消费事件流,所有状态变更走对话面
- **影响**:投影可随时重建,崩溃恢复成本低

### 4. 配置热重载只支持最新 shape

- **为什么**:运行时兼容旧 shape 会引入 shim 与 fallback,违反核心规则
- **怎么做**:旧配置由 doctor 迁移,运行时只读当前规范
- **影响**:升级前必须跑 doctor,否则热重载会失败

### 5. 凭据不落日志不落错误

- **为什么**:凭据是最高敏感数据,日志泄漏等同凭证泄漏
- **怎么做**:凭据规划器只产出引用,日志只记引用 ID
- **影响**:排查凭据问题需用专门诊断面,不能靠 grep 日志

### 6. 执行审批是危险命令的硬门

- **为什么**:Agent 可能执行破坏性命令,无人审批会失控
- **怎么做**:危险命令分类匹配,需操作者显式授权
- **影响**:审批未决时命令阻塞,不静默放行

## 设计观察

### 为什么把聊天显示从对话面拆出

```
错误设计:
   对话面 ──直接渲染──► 客户端
   → 对话面耦合 Markdown / 附件 / 中止 UI 规则
   → 换个渠道(纯文本 SMS)要改对话内核
   → 中止逻辑混入 Turn 状态机

正确设计:
   对话面 ──事件流──► 显示投影 ──► 客户端
   → 对话面只产出语义事件
   → 投影面按渠道特性渲染
   → 中止是投影面与对话面之间的协议,不污染 Turn
```

### 为什么 Control UI 后端独立成面

```
错误设计:
   把 UI 后端逻辑塞进通用 HTTP 处理器
   → UI 路由与 API 路由混在一起
   → CSP / 沙箱策略无法专门强化
   → 插件 Tab 隔离缺失

正确设计:
   Control UI 后端独立子面
   → 专用 CSP 策略
   → 专用路由层(支持 PRS / GitHub 预览)
   → 插件 Tab 沙箱隔离
   → 与通用 API 物理分离
```

### 为什么凭据用规划器而非直接读取

```
错误设计:
   认证面 ──直接读凭据文件──► 校验
   → 多种凭据来源(env / 文件 / secret store)各写一遍
   → 优先级冲突无法解决
   → 凭据泄漏面大

正确设计:
   认证面 ──► 凭据规划器 ──► 校验
              ↑
         统一解析多来源
         统一优先级
         统一脱敏
   → 认证面只拿规划后的材料
   → 凭据来源变化只改规划器
```
