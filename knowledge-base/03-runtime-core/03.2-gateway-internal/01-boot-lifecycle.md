# 01 — 启动与生命周期

> 读完本章你将理解:Gateway 内部如何分阶段启动、回声守卫防什么、客户端启动就绪检查为何独立、配置热重载如何安全穿越所有内部组件。

## 一句话定位

启动与生命周期是 Gateway 内部编排的"引导扇区":
- 5 阶段启动严格串行,前一阶段失败不进下一阶段
- 回声守卫防止重复启动实例互相抢占
- 客户端启动就绪检查把"连接建立"与"可接受请求"分离
- 配置热重载以计划-恢复双阶段穿越所有内部组件

## 组件清单

启动与生命周期由 4 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **启动编排器** | 5 阶段串行启动,每阶段职责独立 | 阶段顺序固定;前一阶段失败不进下一阶段 |
| **回声守卫** | 防止多实例同时操作同一状态目录 | 抢占失败必须 fail closed,不静默共存 |
| **客户端启动就绪** | 区分"连接已建立"与"可接受业务请求" | 就绪前拒绝业务请求,只允许健康检查 |
| **配置热重载面** | 运行期配置变更安全穿越所有内部组件 | 只支持最新 shape;失败必须可回滚 |

## 关键设计约束

### 1. 5 阶段启动严格串行

- **为什么**:每阶段职责独立,串行便于定位启动失败点
- **怎么做**:前一阶段产出作为后一阶段输入;失败立即终止
- **影响**:插件加载在最后,核心运行时先就绪,插件故障不阻塞核心

### 2. 回声守卫必须 fail closed

- **为什么**:多实例写同一状态目录会导致 SQLite 损坏
- **怎么做**:抢占锁失败立即报错退出,不静默共存
- **影响**:运维必须确保单实例运行,不能"再开一个试试"

### 3. 客户端启动就绪前拒绝业务请求

- **为什么**:未就绪时接受请求会导致依赖未加载的组件
- **怎么做**:就绪门只放行健康检查与只读配置查询
- **影响**:负载均衡器需配合就绪探针,避免过早路由流量

### 4. 配置热重载只支持最新 shape

- **为什么**:运行时兼容旧 shape 会引入 shim 与 fallback
- **怎么做**:旧配置由 doctor 迁移,热重载只读当前规范
- **影响**:升级前必须跑 doctor,否则热重载会失败

### 5. 热重载失败必须可回滚

- **为什么**:半应用状态的配置会让组件行为不一致
- **怎么做**:重载恢复模块回滚已刷新组件到旧 revision
- **影响**:操作者需关注重载状态机,失败后排查根因

### 6. 启动 checkpoint 落状态层

- **为什么**:下次启动需比对上次 applied-revision 决定是否迁移
- **怎么做**:启动完成时记录 checkpoint 到共享状态库
- **影响**:状态库损坏会影响启动决策,需 doctor 修复

## 设计观察

### 为什么把客户端启动就绪从认证拆出

```
错误设计:
   客户端连接 + 认证通过 → 立即可发业务请求
   → 插件尚未加载,Turn 无法执行
   → 模型配置尚未应用,LLM 调用失败
   → 错误难定位(看起来认证成功但请求失败)

正确设计:
   客户端连接 + 认证通过 → 进入门控
   门控等待:插件就绪 + 配置应用 + 内部组件就绪
   → 就绪后才放行业务请求
   → 就绪前只允许健康检查
```

### 为什么配置热重载用计划-恢复双阶段

```
错误设计:
   配置变更 → 直接通知所有组件刷新
   → 组件 A 成功,组件 B 失败
   → 系统进入半应用状态
   → 行为不一致,难回滚

正确设计:
   配置变更 → 计划模块(diff + 影响分析)
          → 分发刷新指令
          → 收集结果
          → 全成功才提交,任一失败全回滚
   → 系统始终处于一致状态
```

### 为什么回声守卫不能"软共存"

```
错误设计:
   进程 B 抢占锁失败 → 降级为只读模式继续运行
   → 看似安全,实则:
     • 两个进程都读同一配置
     • 进程 A 写状态,进程 B 缓存失效
     • 运维以为只有一个进程在跑
   → 隐性数据不一致

正确设计:
   抢占失败 → fail closed → 报错退出
   → 运维明确知道只能有一个实例
   → 需要多实例时用独立状态目录
```
