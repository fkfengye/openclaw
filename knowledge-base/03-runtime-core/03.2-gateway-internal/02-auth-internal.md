# 02 — 认证内部

> 读完本章你将理解:Gateway 内部认证面如何把 7 种认证方法归一为单一结果、限速策略如何防止暴力破解、表面解析如何决定客户端可见能力、令牌解析如何处理多来源冲突。

## 一句话定位

认证内部是 Gateway 内部的"边境检查站":
- 7 种认证方法(Bearer / password / cookie / tailscale / device / mcp / plugin)归一为单一结果
- 限速策略按表面与身份双重维度防暴力破解
- 表面解析决定客户端能看到哪些能力与方法
- 令牌解析统一处理多来源冲突,不留模糊优先级

## 组件清单

认证内部由 7 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **表面解析器** | 判断请求来自哪类客户端表面,决定可见能力集 | 表面决定能力,不靠客户端自报 |
| **认证方法集** | 7 种认证方法各自实现,产出归一结果 | 所有方法产出同一形状结果 |
| **归一化器** | 把方法产出统一为下游可消费的认证结果 | 不可旁路,下游只认归一结果 |
| **限速策略器** | 按表面与身份双维度限速,防暴力破解 | 限速在认证前生效,防未认证 floods |
| **模式策略器** | 决定当前部署中哪些认证方法可用 | 方法不可用即拒绝,不静默降级 |
| **安装策略器** | 决定首次安装时允许的认证配置 | 安装时锁定基线,运行时不放宽 |
| **令牌来源冲突解决器** | 多来源令牌同时存在时统一选择 | 不留模糊优先级,显式决策 |

### 限速策略的双重维度

```
   请求到达
       │
       ▼
   ┌──────────────────────────────────────────────┐
   │  限速策略器                                  │
   │                                              │
   │  维度 1:表面维度                            │
   │  • Control UI 表面:宽松配额                │
   │  • OpenAI 兼容表面:按 API key 配额         │
   │  • 插件 HTTP 表面:按插件 ID 配额           │
   │                                              │
   │  维度 2:身份维度                            │
   │  • 已认证身份:按身份配额                   │
   │  • 匿名(未认证):按 IP 严格配额           │
   └──────────────────────────────────────────────┘
       │
       │ 限速通过 → 进入认证方法集
       │ 限速拒绝 → 直接返回 429
       ▼
   ┌──────────────────────────────────────────────┐
   │  认证方法集                                  │
   └──────────────────────────────────────────────┘

   反例(错误设计):
   只按身份限速 → 未认证 floods 不受控
   只按表面限速 → 单个身份跨表面滥用不受控
```

### 令牌来源冲突场景

```
场景:一个请求同时携带 Bearer token 和 Cookie
      两个都有效,但指向不同身份

错误做法(模糊优先级):
   if (Bearer 有效) 用 Bearer
   else if (Cookie 有效) 用 Cookie
   → 优先级隐含在代码顺序里,难以推理
   → 攻击者可用低权限令牌覆盖高权限会话

正确做法(显式解决):
   ┌──────────────────────────────────────┐
   │  令牌来源冲突解决器                  │
   │  • 检测到多来源令牌                  │
   │  • 按显式策略选择(如:拒绝混合)   │
   │  • 或按表面决定优先来源              │
   │  • 记录冲突事件供审计                │
   └──────────────────────────────────────┘
   → 不留模糊,显式决策
```

## 关键设计约束

### 1. 归一结果不可旁路

- **为什么**:7 种方法若各自返回不同结构,下游无法统一处理
- **怎么做**:所有方法产出同一形状的认证结果,下游只认归一结果
- **影响**:新增认证方法只需实现归一接口,下游无需改动

### 2. 表面决定能力,不可客户端自报

- **为什么**:客户端自报能力会让任何客户端都能声称有全部能力
- **怎么做**:表面解析器根据请求特征判断表面,据此决定可见能力集
- **影响**:同一身份在不同表面可见能力不同(如 CLI vs OpenAI 兼容)

### 3. 限速在认证前生效

- **为什么**:未认证 floods 会耗尽资源,认证后才限速为时已晚
- **怎么做**:按表面 + 来源 IP 先做限速,通过后再进认证方法集
- **影响**:匿名请求有严格配额,防止未认证暴力破解

### 4. 方法不可用即拒绝,不静默降级

- **为什么**:静默降级会让安全基线无声放宽
- **怎么做**:模式策略器过滤不可用方法,该方法请求直接拒绝
- **影响**:启用新方法需操作者显式配置,不自动启用

### 5. 令牌来源冲突必须显式解决

- **为什么**:模糊优先级会让攻击者用低权限令牌覆盖高权限会话
- **怎么做**:令牌来源冲突解决器显式选择,记录冲突事件
- **影响**:混合令牌请求可能被拒绝,需客户端清理冗余凭据

### 6. 安装策略锁定基线,运行时不放宽

- **为什么**:运行时自动放宽会让安全基线被无声侵蚀
- **怎么做**:安装策略器在首次安装时锁定基线,运行时只能收紧
- **影响**:放宽需操作者显式操作,有审计痕迹

## 设计观察

### 为什么把表面解析从认证方法拆出

```
错误设计:
   认证方法内部各自判断表面
   → Bearer 方法判断一次,Cookie 方法判断一次
   → 判断逻辑可能不一致
   → 可见能力集散落在各方法里

正确设计:
   表面解析器统一判断 → 产出表面类型
   认证方法只关心凭据校验
   可见能力集由表面决定,与具体方法无关
   → 判断逻辑集中,可审计
```

### 为什么限速要双重维度

```
错误设计:
   只按身份限速
   → 未认证请求(无身份)无法限速
   → 暴力破解密码时不受控

   只按表面限速
   → 单个身份跨多个表面滥用不受控
   → 一个 API key 打爆多个表面

正确设计:
   表面维度 + 身份维度双重限速
   → 未认证按 IP 严格限速
   → 已认证按身份配额
   → 跨表面滥用受身份维度约束
```

### 为什么安装策略与运行时分离

```
错误设计:
   运行时可随时启用新认证方法
   → 某次配置错误自动启用了不安全方法
   → 安全基线被无声放宽
   → 无人知道何时发生

正确设计:
   安装策略器在首次安装时锁定基线
   运行时只能在基线内调整
   放宽需操作者显式操作
   → 安全基线变更可审计
```
