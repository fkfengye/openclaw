# 03 — 客户端与对话

> 读完本章你将理解:Gateway 内部如何管理客户端连接生命周期、Turn 如何编排一条消息的来回、对话列表与读取如何工作、错误如何统一归一化保证失败可恢复。

## 一句话定位

客户端与对话是 Gateway 内部的"会话中枢":
- 客户端连接生命周期由注册表统一管理,断线可恢复
- Turn 编排把一条用户消息变成一次 Agent 调用与回复
- 对话列表/读取/发送各自独立,共享会话身份
- 错误归一化器把各种失败信号统一为可恢复结果

## 组件清单

客户端与对话由 7 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **客户端注册表** | 管理所有活跃连接的生命周期 | 断线重连保留会话身份,不重建 |
| **Turn 编排器** | 一条消息的完整来回(接收→准备→调 Agent→收回复→归一) | 同会话串行,跨会话并发 |
| **对话发送器** | 把用户输入投递到 Agent,处理排队 | 排队 Turn 不丢失,按序执行 |
| **对话列表器** | 列出会话历史,支持分页与过滤 | 列表只读,不改状态 |
| **对话读取原点器** | 追溯消息来源(渠道/会话/Turn) | 原点不可伪造,用于审计 |
| **错误归一化器** | 把各种失败统一为可恢复结果 | 失败可重试,不丢上下文 |
| **会话身份管理** | 会话标识的创建、绑定、迁移 | 会话身份与连接解耦 |

### 客户端连接生命周期

```
   ┌──────────────────────────────────────────────────────┐
   │  客户端连接生命周期                                  │
   │                                                      │
   │   ┌────────┐    ┌────────┐    ┌────────┐            │
   │   │ 注册   │───►│ 活跃   │───►│ 断线   │            │
   │   └────────┘    └────┬───┘    └────┬───┘            │
   │                      │             │                 │
   │                      │             │ ┌──────────────┐│
   │                      │             └─►  恢复重连    ││
   │                      │               └──────┬───────┘│
   │                      │                      │         │
   │                      │◄─────────────────────┘         │
   │                      │                                │
   │                      ▼                                │

   │                 └────────┘                            │

   关键:断线 ≠ 注销
```

### 对话读取原点器的作用

```
   一条消息有多个维度身份:

   ┌──────────────────────────────────────────┐
   │  消息                                    │
   │  • 消息 ID:唯一标识                     │
   │  • 会话 ID:属于哪个会话                 │
   │  • Turn ID:属于哪次来回                 │
   │  • 渠道原点:来自 Telegram / UI / CLI   │
   │  • 创建时间                              │
   └──────────────────────────────────────────┘

   读取原点器用途:
   • 审计:追溯消息从哪来
   • 路由:回复回原渠道
   • 过滤:按原点筛选历史
   • 防伪:原点不可客户端伪造

   反例(错误设计):
   客户端自报原点 → 任何客户端可伪造来源
   → 必须由系统在接收时记录,不可客户端自报
```

### 错误归一化器如何统一失败

```
   Turn 执行过程中可能发生的失败:
   • Agent 超时
   • 用户取消
   • LLM 调用失败
   • 工具执行失败
   • 状态库写入失败
   • 网络中断

            │
            ▼
   ┌──────────────────────────────────────────┐
   │  错误归一化器                            │
   │                                          │
   │  输入:各种失败信号                      │
   │  输出:统一可恢复结果                    │
   │  • 终态类型(超时/取消/错误/正常)      │
   │  • 原因                                  │
   │  • 是否可重试                            │
   │  • 上下文保留情况                        │
   └──────────────────────────────────────────┘
            │
            ▼
   下游(投影 / 客户端)只认归一结果
   不关心具体失败类型

   反例(错误设计):
   各处自行判断失败 → 同一失败在不同视角看到不同结果
   → 必须单一入口归一化
```

### 断线重连场景

```
用户在 Control UI 对话中途网络断开
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 客户端注册表检测到断线                                    │
│    • 连接状态:活跃 → 断线                                  │
│    • 会话身份保留(不注销)                                 │
│    • Turn 仍在后台执行(如未取消)                          │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 用户网络恢复,重连                                        │
│    • 重新认证(走认证内部)                                 │
│    • 客户端注册表识别同一会话身份                            │
│    • 状态:断线 → 活跃                                      │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 恢复会话上下文                                            │
│    • 对话列表器拉取历史                                      │
│    • 聊天显示投影重建可见消息                                │
│    • 如 Turn 仍在跑 → 继续接收流式回复                      │
│    • 如 Turn 已结束 → 显示归一终态                          │
└──────────────────────────────────────────────────────────────┘

   关键:断线不丢上下文
   • 会话身份与连接解耦
   • Turn 不因连接断开而取消(除非用户显式取消)
   • 重连后可继续看到完整历史
```

### 排队 Turn 场景

```
用户连续快速发送 3 条消息
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 对话发送器收到 3 条消息                                      │
│ • 消息 1 → 立即投递 Turn 编排器(开始执行)                │
│ • 消息 2 → 排队(等 Turn 1 完成)                           │
│ • 消息 3 → 排队(等 Turn 2 完成)                           │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
   Turn 1 执行中 → 完成 → Turn 2 开始 → 完成 → Turn 3 开始
   (同会话严格串行,避免状态竞争)

   反例(错误设计):
   3 条消息并发执行 → 同时写会话历史 → 状态竞争
   → 必须同会话串行
```

## 关键设计约束

### 1. 同会话串行,跨会话并发

- **为什么**:同会话并发写状态会导致历史错乱
- **怎么做**:按会话身份分配 lane,同会话排队
- **影响**:用户连续发多条消息会排队,但不会丢失

### 2. 会话身份与连接解耦

- **为什么**:网络抖动不应导致会话丢失
- **怎么做**:会话身份独立于连接,断线保留,重连恢复
- **影响**:用户体验稳定,后台 Turn 不因断线取消

### 3. 错误归一化是硬约束

- **为什么**:各种失败若各自处理会导致不一致
- **怎么做**:所有失败信号经单一入口归一为可恢复结果
- **影响**:下游只认归一结果,失败可重试不丢上下文

### 4. 读取原点不可客户端伪造

- **为什么**:伪造原点会让审计与路由失效
- **怎么做**:原点由系统在接收时记录,不采信客户端自报
- **影响**:消息来源可追溯,路由回原渠道可靠

### 5. 对话列表只读

- **为什么**:列表操作不应副作用改状态
- **怎么做**:列表器只查询,不写;写操作走发送器
- **影响**:列表调用安全,不影响会话进行

### 6. Turn 终态归一化与 Agent 终态归一化对齐

- **为什么**:Turn 是 Agent 的上层封装,终态语义需一致
- **怎么做**:Turn 归一化器消费 Agent 归一化结果,不重推优先级
- **影响**:避免两层各自判断导致冲突

## 设计观察

### 为什么把 Turn 编排从对话发送拆出

```
错误设计:
   对话发送器内部直接调 Agent
   → 发送逻辑与 Turn 状态机耦合
   → 排队 / 中止 / 重试逻辑混在发送里
   → 难以单独测试 Turn 行为

正确设计:
   对话发送器只负责投递
   Turn 编排器负责完整来回
   → 发送逻辑简单
   → Turn 状态机可独立测试
   → 排队 Turn 由发送器管理,不污染 Turn
```

### 为什么错误归一化要独立组件

```
错误设计:
   Turn 各阶段各自处理失败
   → 接收失败返回一种结构
   → 准备失败返回另一种结构
   → Agent 失败又一种结构
   → 下游需处理 N 种失败形状

正确设计:
   所有失败 → 错误归一化器 → 统一可恢复结果
   → 下游只处理一种形状
   → 失败可重试,上下文保留情况明确
```

### 为什么会话身份与连接解耦

```
错误设计:
   连接断开 → 会话注销 → 重连重建会话
   → 历史丢失(或需重新加载)
   → 后台 Turn 取消
   → 用户体验差

正确设计:
   连接断开 → 会话身份保留 → 重连恢复
   → 历史完整
   → 后台 Turn 继续
   → 网络抖动对用户透明
```
