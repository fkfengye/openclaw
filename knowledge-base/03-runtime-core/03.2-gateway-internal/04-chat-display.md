# 04 — 聊天显示

> 读完本章你将理解:Gateway 内部如何把 Turn 事件流投影为可见消息、附件如何处理、用户中止如何介入、排队 Turn 如何展示、输入与输出为何需要双向清洗。

## 一句话定位

聊天显示是 Gateway 内部的"渲染层":
- 投影核心把事件流累积为可见消息,只读不可写回状态
- 附件处理统一图片/文件的引用与展示
- 中止处理器让用户中途取消,不污染 Turn 状态机
- 排队 Turn 展示让用户知道消息在排队
- 输入清洗与输出清洗双向保护用户与系统

## 组件清单

聊天显示由 6 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **投影核心** | 累积事件流为可见消息,分阶段处理 | 只读事件流,不写回状态 |
| **附件处理器** | 统一图片/文件的引用与展示 | 引用不内联,大文件不堵流 |
| **中止处理器** | 用户中途取消的介入点 | 中止是投影与对话的协议,不污染 Turn |
| **排队 Turn 展示器** | 展示排队中的 Turn 状态 | 排队状态实时更新,执行时切换 |
| **输入清洗器** | 用户输入净化后投递 | 移除注入风险,保留语义 |
| **输出清洗器** | 系统输出净化后展示 | 移除敏感片段,保留可读性 |

### 中止处理器与 Turn 的协议

```
   用户在 Turn 执行中点"中止"
            │
            ▼
   ┌──────────────────────────────────────────────┐
   │  中止处理器                                  │
   │                                              │
   │  • 接收用户中止意图                         │
   │  • 通知 Turn 编排器(不直接杀 Agent)       │
   │  • Turn 编排器进入取消流程                  │
   │  • 终态归一化为"取消"                       │
   │  • 投影核心展示已收部分                     │
   └──────────────────────────────────────────────┘

   关键:中止不绕过终态归一化
   • 中止是请求,不是强制杀
   • Turn 仍经终态归一化器产出"取消"终态
   • 投影展示已收部分 + 取消标记

   反例(错误设计):
   中止直接杀 Agent → 无终态 → 投影不知如何展示
   → 必须经 Turn 编排器的取消流程
```

   │  输出方向                                            │
   │                                                      │
   │  投影核心 ──► 输出清洗器 ──► 净化输出 ──► 客户端   │

## 协作流程

### 一次流式回复的投影旅程

下面追踪 Turn 事件流如何被投影为用户看到的流式回复。

```
Turn 编排器开始执行,产生事件流
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 投影核心接收事件流                                        │
│    • 第一个 chunk 到达                                       │
│    • 创建新消息容器                                          │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 累积 chunk                                                │
│    • 每个 chunk 追加到消息文本                               │
│    • 实时推送到客户端(流式显示)                            │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 遇到 tool call                                            │
│    • 投影展示"正在调用工具"标记                             │
│    • 工具执行中(由 Agent 运行时处理)                       │
│    • 工具结果返回 → 继续接收 chunk                          │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. Turn 完成                                                 │
│    • 投影核心收到完成事件                                    │
│    • 消息容器定稿                                            │
│    • 进入输出清洗                                            │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 5. 输出清洗                                                  │
│    • 移除敏感片段(如内部标记)                             │
│    • 移除不应展示的内部状态                                 │
│    • 保留可读性                                              │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
                  客户端看到完整的流式回复
                  (含工具调用标记 + 最终文本)
```

## 关键设计约束

### 1. 投影只读不可写回状态

- **为什么**:投影是事件流的派生物,写回状态会破坏事件溯源
- **怎么做**:投影面只消费事件流,所有状态变更走对话面
- **影响**:投影可随时重建,崩溃恢复成本低

### 2. 中止是协议不是强制杀

- **为什么**:直接杀 Agent 会导致无终态,投影不知如何展示
- **怎么做**:中止处理器通知 Turn 编排器,经终态归一化产出"取消"
- **影响**:中止后展示一致(已收部分 + 取消标记)

### 3. 双向清洗对称存在

- **为什么**:只清洗输出会留输入注入风险,只清洗输入会泄漏内部状态
- **怎么做**:输入清洗器与输出清洗器对称存在,各司其职
- **影响**:用户与系统双向保护

### 4. 附件引用不内联

- **为什么**:内联大文件会堵流,且引用丢失
- **怎么做**:附件处理器产出引用,消息文本只含引用标识
- **影响**:客户端按需加载,引用稳定可追溯

### 5. 排队 Turn 状态可见

- **为什么**:用户需知道消息会被处理,不是丢了
- **怎么做**:排队 Turn 展示器实时更新排队状态,执行时切换
- **影响**:用户体验稳定,不会重复发送

### 6. 投影分阶段处理

- **为什么**:不同类型内容(核心/历史/画布/消息工具)处理逻辑不同
- **怎么做**:投影核心分阶段处理,每阶段职责独立
- **影响**:新增内容类型只需加阶段,不改核心逻辑

## 设计观察

### 为什么把投影从对话面拆出

```
错误设计:
   对话面 ──直接构造可见消息──► 客户端
   → 对话面耦合显示规则
   → 换渠道(纯文本 SMS)要改对话内核
   → 中止逻辑混入 Turn 状态机

正确设计:
   对话面 ──事件流──► 投影核心 ──► 客户端
   → 对话面只产出语义事件
   → 投影面独立演进显示规则
   → 中止是投影与对话的协议
```

### 为什么中止不直接杀 Agent

```
错误设计:
   用户点中止 → 直接杀 Agent 进程 / 取消 LLM 请求
   → Agent 无终态 → 状态库不知如何记录
   → 投影不知展示什么(全丢?展示已收?)
   → 资源清理可能不完整

正确设计:
   用户点中止 → 中止处理器 → 通知 Turn 编排器
   → Turn 编排器进入取消流程 → 终态归一化为"取消"
   → 投影展示已收部分 + 取消标记
   → 状态库记录"取消"终态
```

### 为什么附件用引用而非内联

```
错误设计:
   图片直接内联到消息文本(base64)
   → 大图片堵流(消息体巨大)
   → 多次展示需多次传输
   → 引用丢失,无法追溯

正确设计:
   附件处理器产出引用
   消息文本只含引用标识
   客户端按需加载引用内容
   → 消息体小,流式顺畅
   → 引用稳定,可追溯
   → 客户端可决定加载时机
```
