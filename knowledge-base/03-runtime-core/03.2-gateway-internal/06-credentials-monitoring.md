# 06 — 凭据与监控

> 读完本章你将理解:Gateway 内部如何规划凭据、设备如何认证、渠道健康如何监控、定时流如何按计划触发对话、执行审批如何拦截危险命令。

## 一句话定位

凭据与监控是 Gateway 内部的"横向守护面":
- 凭据规划器统一解析多来源凭据,为认证面提供材料
- 设备认证管理远程节点的配对与授权
- 渠道健康监控渠道投递状态,故障可观测
- 定时流按计划触发对话,产物回流对话面
- 执行审批是危险命令的硬门,不静默放行

## 组件清单

凭据与监控由 6 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **凭据规划器** | 多来源凭据统一解析,优先级统一,脱敏 | 凭据不落日志,只产出引用 |
| **设备认证器** | 远程节点配对、设备授权、元数据规范化 | 配对需显式授权,不自动批准 |
| **凭据密钥输入** | 密钥引用管理,解析密钥输入路径 | 密钥不内联,用引用 |
| **渠道健康监控器** | 监控渠道投递状态,故障告警,健康策略 | 健康状态可观测,故障不静默 |
| **定时流** | 按计划触发对话,产物回流,退出监视 | 触发有日志,失败可重试 |
| **执行审批器** | 危险命令拦截,显式授权,iOS 推送通知 | 审批未决时阻塞,不静默放行 |

## 关键设计约束

### 1. 凭据不落日志不落错误

- **为什么**:凭据是最高敏感数据,日志泄漏等同凭证泄漏
- **怎么做**:凭据规划器只产出引用,日志只记引用 ID
- **影响**:排查凭据问题需用专门诊断面,不能靠 grep 日志

### 2. 设备配对需显式授权

- **为什么**:自动批准会让任意设备可接入
- **怎么做**:配对请求需操作者确认,不自动批准
- **影响**:新设备接入有审计痕迹

### 3. 渠道故障不静默

- **为什么**:静默故障会让操作者不知渠道挂了,消息丢失无感知
- **怎么做**:健康监控器检测到故障必告警,通知 Control UI
- **影响**:操作者能及时响应渠道问题

### 4. 定时流复用对话流程

- **为什么**:另起一套执行路径会导致行为不一致
- **怎么做**:定时流触发对话 Turn,走正常对话流程
- **影响**:定时流产物走同一投影面,失败走同一错误归一化

### 5. 执行审批是硬门不静默放行

- **为什么**:Agent 可能执行破坏性命令,无人审批会失控
- **怎么做**:危险命令分类匹配,需操作者显式授权,未决时阻塞
- **影响**:审批未决时命令阻塞,超时按策略处理(默认拒绝)

### 6. 凭据多来源优先级显式

- **为什么**:模糊优先级会让凭据选择不可预测
- **怎么做**:凭据规划器显式策略选择来源,不留模糊
- **影响**:凭据来源变化行为可预测,可审计

## 设计观察

### 为什么凭据用规划器而非直接读取

```
错误设计:
   认证面 ──直接读凭据文件──► 校验
   → 多种凭据来源各写一遍
   → 优先级冲突无法解决
   → 凭据泄漏面大

正确设计:
   认证面 ──► 凭据规划器 ──► 校验
              ↑
         统一解析多来源
         统一优先级
         统一脱敏
   → 认证面只拿规划后的材料
   → 凭据来源变化只改规划器
```

### 为什么执行审批不自动放行危险命令

```
错误设计:
   危险命令自动放行(信任 Agent)
   → Agent 执行 rm -rf / → 灾难
   → Agent 被 prompt injection → 执行恶意命令
   → 无审计痕迹

正确设计:
   危险命令 → 执行审批器 → 操作者显式授权
   → 人为干预拦截危险操作
   → 审批决策有记录
   → 超时默认拒绝(保守)
```

### 为什么渠道健康必须告警

```
错误设计:
   渠道故障静默(只记日志)
   → 操作者不查日志就不知渠道挂了
   → 消息丢失无感知
   → 用户以为消息发出去了

正确设计:
   渠道故障 → 健康监控器告警
   → Control UI 健康面板更新
   → 操作者能及时响应
   → 不健康渠道状态可见
```
