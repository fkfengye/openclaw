# 00 — Hook 系统总览

> 这是 Hook 系统目录的入口。读完本章你将理解:OpenClaw Hook 系统的整体构成、四类 Hook 来源如何分层协作、Hook 从配置到加载到执行的完整链路,以及为何 Hook 是插件能力之外的延伸层而非插件本身。

## 一句话定位

Hook 系统是 OpenClaw 运行时的**事件驱动延伸层**:
- 监听 Agent 生命周期、Gateway 启动、会话流转等内部事件,在事件点执行用户自定义逻辑
- 四类来源(打包内置 / 插件提供 / 托管安装 / 工作区本地)按优先级与信任策略分层
- 配置、加载、安装、执行各成一层,核心运行时不绑定任何具体 Hook

## 组件清单

Hook 系统由 3 层共 9 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **配置读取器** | 读取 Hook 配置,评估环境变量与配置路径是否满足 | Hook 专属默认值,不污染全局配置 |
| **启用策略裁决器** | 决定单个 Hook 是否可运行,处理来源优先级与覆盖关系 | 四类来源有固定优先级表,工作区来源默认不开启 |
| **前置元数据解析器** | 从 Hook 描述文件解析事件声明、OS 限制、依赖要求、安装规格 | 描述文件只解析前置块,有大小上限防 OOM |
| **配置聚合计** | 把配置块、安装记录、遗留处理器合并为可加载 Hook 集合 | 遗留处理器只为兼容,新配置走规范路径 |
| **状态汇总器** | 汇总已配置、已安装、插件提供的 Hook,标注缺失依赖与未知事件 | 标注未知事件以提示拼写错误 |
| **目录发现器** | 从四类来源目录发现 Hook 描述文件与处理器模块 | 来源信任级别决定是否警告加载本地代码 |
| **模块加载器** | 把 Hook 处理器模块导入进程,处理缓存隔离 | 不可变来源跳过缓存破坏,可变来源按文件元数据破坏缓存 |
| **安装服务** | 从归档或 npm 规格安装 Hook 包,写安装记录到机器状态 | 安装前做安全扫描,记录完整性漂移 |
| **即发即忘执行器** | 异步调度 Hook 任务,不阻塞热路径 | 有界并发(16)、有界队列(256)、超时(2s) |

## 协作流程

### Gateway 启动时加载 Hook 的完整旅程

下面追踪 Gateway 启动阶段 5(插件加载)中,Hook 系统如何把四类来源的 Hook 加载到事件总线。

```
Gateway 启动阶段 5 开始
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 配置与策略层                                               │
│    → 读取 Hook 配置块(内部 Hook 启用状态、条目、额外目录)   │
│    → 读取机器状态中的安装记录                                 │
│    → 合并配置与安装记录,判断是否有可加载内部 Hook            │
│    → 若全部禁用则跳过后续步骤                                 │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 目录发现层                                                 │
│    按四类来源并行发现:                                       │
│    ├─ 打包内置目录(随发布物打包,不可变)                    │
│    ├─ 插件提供目录(从插件 manifest 声明中解析)              │
│    ├─ 托管安装目录(用户通过安装命令安装的 Hook 包)          │
│    └─ 工作区目录(本地开发用,显式启用才加载)                │
│    → 每个来源读取 Hook 描述文件,解析前置元数据              │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 策略裁决                                                   │
│    → 同名 Hook 按来源优先级保留高者,忽略低者                 │
│    → 评估每个 Hook 的启用状态(配置开关 + 来源默认模式)      │
│    → 评估运行时资格(OS / 二进制 / 环境变量 / 配置路径)      │
│    → 输出:最终可加载 Hook 列表                                │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 模块加载层                                                 │
│    → 对每个可加载 Hook,构建导入 URL                          │
│      (不可变来源跳过缓存破坏,可变来源按文件元数据破坏)      │
│    → 动态导入处理器模块                                       │
│    → 解析导出的处理函数(默认导出或指定导出名)               │
│    → 工作区/托管来源加载时打警告日志(本地受信代码)          │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 5. 事件总线注册                                               │
│    → 把处理器按事件类型注册到内部事件总线                    │
│    → 记录已加载的注册项,供进程重启时清理                     │
│    → Gateway 就绪后,事件到达即触发对应处理器                │
└──────────────────────────────────────────────────────────────┘
```

### 一次内部事件触发 Hook 的执行流程

```
Agent 生命周期事件产生(如会话启动)
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 事件总线接收事件                                           │
│    → 按事件类型查找已注册的处理器                             │
│    → 若无处理器则直接返回(不报错)                           │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 即发即忘调度                                               │
│    → 把任务放入有界队列(最大 256)                           │
│    → 若并发未满(最大 16)则立即执行,否则排队                │
│    → 设置超时(默认 2 秒)                                   │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 处理器执行                                                 │
│    → 调用 Hook 处理函数,传入事件上下文                       │
│    → 超时则终止并记日志,不抛出到调用方                       │
│    → 异常被捕获并截断日志(最大 500 字符)                    │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 释放并发槽                                                 │
│    → 从队列取下一个任务执行                                  │
│    → 不阻塞 Agent Runner 主流程                              │
└──────────────────────────────────────────────────────────────┘
```

## 关键设计约束

### 1. 四类来源有固定优先级与信任策略

- **为什么**:防止同名 Hook 冲突时行为不确定,同时区分受信代码与本地代码
- **怎么做**:打包内置 < 插件提供 < 托管安装 < 工作区本地,高优先级覆盖低优先级;工作区来源默认不开启
- **影响**:用户可通过工作区 Hook 覆盖内置行为,但必须显式启用并接受警告

### 2. 不可变来源跳过缓存破坏

- **为什么**:打包内置 Hook 在两次安装间不变,跳过缓存破坏让 V8 复用模块缓存,加速重启
- **怎么做**:仅打包内置来源的导入 URL 不附加查询参数;其他来源按文件修改时间与大小生成缓存键
- **影响**:Gateway 重启时内置 Hook 加载更快,可变来源的修改能被正确感知

### 3. 即发即忘执行不阻塞热路径

- **为什么**:Hook 是延伸逻辑,不应拖慢 Agent 主流程或 Gateway 启动
- **怎么做**:有界并发(16)、有界队列(256)、超时(2 秒),异常被捕获不外抛
- **影响**:Hook 执行失败或超时只影响自身,不影响 Agent 回复或消息投递

### 4. 安装记录持久化到机器状态

- **为什么**:安装的 Hook 包需跨进程重启可见,且不能存为 JSON 文件(违反状态层规则)
- **怎么做**:安装记录写入共享状态库的机器状态表,运行时只读规范记录
- **影响**:卸载/更新 Hook 时以机器状态为准,不依赖文件系统扫描

### 5. 描述文件只解析前置元数据

- **为什么**:Hook 描述文件可能来自不可信包,需防止恶意大文件 OOM
- **怎么做**:只解析前置块,设置 1MB 上限,超出则拒绝
- **影响**:Hook 包的正文内容不被读取,只消费元数据

### 6. 工作区来源加载时必须警告

- **为什么**:工作区 Hook 是本地受信代码,直接加载进 Gateway 进程,用户需知情
- **怎么做**:加载工作区或托管来源时打子系统日志警告
- **影响**:用户能从日志看到本地代码被加载,不会静默执行

## 设计观察

### 为什么 Hook 不直接是插件

```
错误设计:
   把 Hook 合并进插件系统 → 插件需声明 Hook 目录,插件卸载则 Hook 消失

正确设计:
   ┌──────────────┐         ┌──────────────┐
   │  插件系统    │ ──声明──► │  Hook 系统   │
   │  (能力登记)  │          │  (事件延伸)  │
   └──────────────┘         └──────────────┘
   • 插件可声明 Hook 目录(来源之一)
   • Hook 也可独立安装(不依赖插件)
   • Hook 卸载不影响插件,插件卸载不影响托管 Hook
```

- Hook 是事件驱动的延伸逻辑,插件是能力登记,关注点不同
- 同一个 Hook 可来自四类来源,插件只是其中之一
- Hook 有自己的安装、更新、优先级体系,与插件生命周期解耦

### 为什么用优先级覆盖而非报错

```
错误设计:
   同名 Hook 冲突时报错 → 用户无法用工作区 Hook 覆盖内置行为

正确设计:
   ┌─────────────────────────────────────────────┐
   │  打包内置 Hook "boot-md"                     │
   │           │                                  │
   │           │ 被覆盖(同名高优先级)            │
   │           ▼                                  │
   │  工作区 Hook "boot-md"  → 实际加载这个       │
   └─────────────────────────────────────────────┘
   • 用户可在工作区放同名 Hook 覆盖内置行为
   • 冲突在策略层静默裁决,不阻断启动
   • 状态汇总器会标注哪些 Hook 被覆盖(可观测)
```

### 为什么状态汇总器要标注未知事件

```
场景:Hook 声明了 "command:nwew" 事件(拼写错误,应为 "command:new")

错误设计:
   静默接受 → Hook 永远不触发,用户不知道为什么

正确设计:
   ┌─────────────────────────────────────────────┐
   │  状态汇总器                                  │
   │  • 比对 Hook 声明事件与核心触发点            │
   │  • "command:nwew" 无对应触发点 → 标注未知    │
   │  • 用户在状态报告中看到未知事件 → 发现拼写   │
   └─────────────────────────────────────────────┘
   • 未知事件只在插件也发出该事件时才会触发
   • 标注为可观测信号,不阻断加载
```
