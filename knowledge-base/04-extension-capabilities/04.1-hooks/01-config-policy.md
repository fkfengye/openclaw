# 01 — 配置与策略

> 读完本章你将理解:Hook 的配置如何被读取与归一、四类来源的启用策略如何裁决、描述文件的前置元数据如何被解析、以及状态汇总器如何把可加载 Hook 集合呈现给运维与 Doctor。

## 一句话定位

配置与策略层是 Hook 系统的**准入闸门**:
- 把配置块、安装记录、遗留处理器合并为可加载 Hook 集合
- 按四类来源的固定优先级表裁决同名冲突,按来源默认模式决定是否开启
- 评估运行时资格(OS / 二进制 / 环境变量 / 配置路径),输出最终可加载列表

## 组件清单

配置与策略层由 5 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **配置聚合计** | 把配置块、安装记录、遗留处理器合并,判断是否有可加载内部 Hook | 遗留处理器只为兼容,显式配置优先于全发现 |
| **前置元数据解析器** | 从描述文件前置块解析事件、OS、依赖、安装规格、调用策略 | 只解析前置块,1MB 上限防 OOM |
| **配置读取器** | 评估环境变量、配置路径、二进制是否满足 Hook 运行要求 | Hook 专属默认值,不污染全局配置评估 |
| **启用策略裁决器** | 按来源优先级与默认模式裁决启用状态与同名冲突 | 四类来源固定优先级表,工作区默认不开启 |
| **状态汇总器** | 汇总所有来源 Hook,标注缺失依赖、未知事件、可加载性 | 未知事件标注为可观测信号,不阻断加载 |

### 来源优先级与默认模式的裁决

```
   四类来源的策略表:

   ┌──────────────┬──────────┬────────────┬─────────────────┐
   │  来源        │  优先级  │  默认模式  │  可被谁覆盖     │
   ├──────────────┼──────────┼────────────┼─────────────────┤
   │  打包内置    │   10     │  默认开启  │  插件 / 托管    │
   │  插件提供    │   20     │  默认开启  │  托管           │
   │  托管安装    │   30     │  默认开启  │  仅自身         │
   │  工作区本地  │   40     │  显式启用  │  仅自身         │
   └──────────────┴──────────┴────────────┴─────────────────┘

   裁决流程:

   同名 Hook 到达
        │
        ▼
   ┌───────────────────────────┐
   │  按来源优先级排序         │
   │  保留最高优先级者         │
   │  忽略其余                 │
   └─────────────┬─────────────┘
                 │
                 ▼
   ┌───────────────────────────┐
   │  查保留者的默认模式       │
   │  • 默认开启 → 检查配置开关│
   │  • 显式启用 → 必须配置开启│
   └─────────────┬─────────────┘
                 │
                 ▼
   ┌───────────────────────────┐
   │  输出启用状态             │
   │  + 禁用原因(若禁用)     │
   └───────────────────────────┘

   反例(错误设计):
   ┌─────────────────────────────────────────────┐
   │ 工作区来源默认开启 → 本地代码静默执行        │
   │                                              │
   │ 正确:工作区来源是 explicit-opt-in,          │
   │       默认禁用,需配置显式开启               │
   └─────────────────────────────────────────────┘
```

### 运行时资格评估的三类检查

```
   ┌─────────────────────────────────────────────────────┐
   │  运行时资格评估器                                   │
   │                                                     │
   │  输入:Hook 元数据声明的 requires                    │
   ├─────────────────────────────────────────────────────┤
   │                                                     │
   │  ① OS 检查                                          │
   │     元数据声明 os: [darwin, linux]                  │
   │     → 当前平台不匹配 → 不加载                       │
   │                                                     │
   │  ② 二进制检查                                       │
   │     元数据声明 requires.bins: [gcloud]              │
   │     或 requires.anyBins: [gog, gmail-watch]         │
   │     → 二进制不在 PATH → 不加载                      │
   │                                                     │
   │  ③ 环境变量检查                                     │
   │     元数据声明 requires.env: [GOOGLE_CREDENTIALS]   │
   │     → 环境变量未设且配置块未提供 → 不加载           │
   │                                                     │
   │  ④ 配置路径检查                                     │
   │     元数据声明 requires.config: [gmail.enabled]     │
   │     → 配置路径为假(含 Hook 专属默认值)→ 不加载    │
   │                                                     │
   │  ⑤ always 标记                                      │
   │     元数据声明 always: true                         │
   │     → 跳过运行时资格检查,总是加载                  │
   │                                                     │
   └─────────────────────────────────────────────────────┘

   反例(错误设计):
   ┌─────────────────────────────────────────────┐
   │ 不检查 always → 平台特定 Hook 在错误平台崩溃 │
   │                                              │
   │ 正确:always: true 跳过资格检查,            │
   │       用于必须加载的启动类 Hook              │
   └─────────────────────────────────────────────┘
```

## 协作流程

### 一个 Hook 从配置到可加载的完整裁决

下面追踪一个 Gmail Hook 从配置读取到最终判定可加载的全过程。

```
Gmail Hook(托管安装来源,优先级 30)
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 配置聚合计                                                 │
│    → 读取配置块:internal.enabled 未设(默认)                │
│    → 读取机器状态:有 Gmail 安装记录                          │
│    → 输出:null(全发现模式,让加载层扫描托管目录)           │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 前置元数据解析器                                           │
│    → 从托管目录找到 Gmail 描述文件                            │
│    → 解析前置块:                                             │
│      • events: [gateway:startup]                             │
│      • os: [darwin, linux]                                   │
│      • requires.bins: [gog]                                  │
│      • requires.env: [GOOGLE_CREDENTIALS]                    │
│      • requires.config: [hooks.gmail.enabled]                │
│      • install: [{ kind: npm, package: ... }]                │
│    → 输出:Hook 元数据                                        │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 启用策略裁决器                                             │
│    → 查来源策略:托管安装,优先级 30,默认开启                │
│    → 检查配置开关:hooks.gmail.enabled 未显式禁用             │
│    → 输出:启用状态 = true                                   │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 配置读取器(运行时资格评估)                               │
│    → OS 检查:当前是 linux,匹配 [darwin, linux]             │
│    → 二进制检查:gog 在 PATH                                 │
│    → 环境变量检查:GOOGLE_CREDENTIALS 已设                   │
│    → 配置路径检查:hooks.gmail.enabled 为真                  │
│    → 输出:资格满足 = true                                   │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 5. 状态汇总器                                                 │
│    → 汇总此 Hook 到状态报告                                  │
│    → 标注:可加载 = true,无缺失依赖,无未知事件             │
│    → 标注安装选项(npm 规格)                                │
│    → 输出:可加载 Hook 条目                                  │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
                  (下游:加载与安装层接管)
```

## 关键设计约束

### 1. 来源优先级表是固定的不可配置

- **为什么**:防止用户随意调整优先级导致内置 Hook 被意外屏蔽或冲突裁决不确定
- **怎么做**:四类来源的优先级(10/20/30/40)与覆盖关系在策略模块中硬编码,不读配置
- **影响**:用户只能通过在工作区放同名 Hook(优先级 40)覆盖内置行为,不能调整优先级本身

### 2. 工作区来源必须显式启用

- **为什么**:工作区 Hook 是本地代码,直接加载进 Gateway 进程,默认开启会导致静默执行用户代码
- **怎么做**:工作区来源的默认模式是显式启用,即使配置未禁用也不会自动加载
- **影响**:用户想用工作区 Hook 必须在配置中显式开启,加载时还会打警告日志

### 3. Hook 专属默认值不污染全局配置评估

- **为什么**:某些配置路径(如 browser.enabled)对 Hook 有默认为真的语义,但对全局不一定
- **怎么做**:配置读取器维护 Hook 专属默认值表,只在评估 Hook 资格时叠加,不影响其他模块的配置评估
- **影响**:同一个配置路径在 Hook 上下文和其他上下文可能有不同的默认行为

### 4. 描述文件只解析前置块且有大小上限

- **为什么**:Hook 描述文件可能来自不可信的安装包,全文解析会导致 OOM 或注入风险
- **怎么做**:只解析前置元数据块,设置 1MB 上限,超出则拒绝解析
- **影响**:Hook 包的正文内容(如使用说明)不被运行时消费,仅元数据生效

### 5. 未知事件标注为可观测信号

- **为什么**:Hook 声明的事件名若拼写错误,会永远不触发,用户难以发现
- **怎么做**:状态汇总器比对 Hook 声明事件与核心已知触发点,标注无对应触发点的事件为未知
- **影响**:未知事件不阻断加载(插件也可能发出该事件),但在状态报告中可见

### 6. 遗留处理器只为兼容不新增

- **为什么**:旧版本配置可能有内联处理器声明,需保持兼容但不应扩展
- **怎么做**:配置聚合计在判断可加载性时纳入遗留处理器,但新配置应走规范的安装/描述文件路径
- **影响**:遗留处理器是迁移债务,Doctor 会引导用户迁移到规范路径

## 设计观察

### 为什么用三路合并而非单一配置源

```
错误设计:
   只读配置块 → 安装的 Hook 包不在配置块中则无法加载

正确设计:
   ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
   │  配置块      │  │  安装记录    │  │  遗留处理器  │
   │  (用户编辑) │  │  (机器状态)  │  │  (旧配置)    │
   └──────┬───────┘  └──────┬───────┘  └──────┬───────┘
          │                 │                 │
          └─────────────────┼─────────────────┘
                            │
                            ▼
                   ┌─────────────────┐
                   │  配置聚合计     │
                   │  (三路合并)     │
                   └─────────────────┘
   • 用户安装 Hook 包后不需手动编辑配置块
   • 机器状态记录跨重启可见
   • 遗留配置平滑过渡
```

### 为什么 always 标记跳过资格检查

```
场景:boot-md Hook 需要在 Gateway 启动时无条件运行(注入引导文件)

错误设计:
   boot-md 声明 requires.bins: [some-tool]
   → 某平台没有 some-tool → boot-md 不加载 → 启动缺失引导文件

正确设计:
   ┌─────────────────────────────────────────────┐
   │  boot-md 声明 always: true                  │
   │  → 跳过 OS / 二进制 / 环境变量 / 配置检查   │
   │  → 总是加载,在启动事件中运行                │
   └─────────────────────────────────────────────┘
   • always 是显式契约,不是默认行为
   • 仅用于必须运行的启动类 Hook
   • 状态汇总器仍会标注其依赖状态(可观测)
```

### 为什么禁用原因要显式输出

```
场景:用户配置 hooks.gmail.enabled = false,但不知道为什么 Gmail 不工作

错误设计:
   只输出 enabled: false → 用户不知道是配置关的还是依赖缺失

正确设计:
   ┌─────────────────────────────────────────────┐
   │  启用策略裁决器输出:                        │
   │  • enabled: false                           │
   │  • reason: "disabled in config"             │
   │                                              │
   │  状态汇总器输出:                            │
   │  • loadable: false                          │
   │  • blockedReason: "missing requirements"    │
   │  或 blockedReason: "disabled in config"     │
   │  或 blockedReason: "workspace hook          │
   │     (disabled by default)"                  │
   └─────────────────────────────────────────────┘
   • 三种禁用原因区分清楚:配置关 / 依赖缺 / 工作区默认关
   • Doctor 能根据原因给出针对性修复建议
```
