# 02 — 加载与安装

> 读完本章你将理解:四类来源的 Hook 目录如何被发现、处理器模块如何被导入并注册到事件总线、Hook 包如何从 npm 规格或本地归档安装到机器状态、以及更新机制如何刷新安装记录与配置引用。

## 一句话定位

加载与安装层是 Hook 系统的**运行时落地管道**:
- 从四类来源目录发现 Hook 描述文件与处理器模块,动态导入进程
- 按来源信任级别做缓存隔离(不可变来源跳过,可变来源按文件元数据破坏)
- 安装服务把 Hook 包从 npm 或本地归档装入托管目录,记录写机器状态

## 组件清单

加载与安装层由 5 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **目录发现器** | 从四类来源目录定位 Hook 描述文件与处理器模块 | 打包内置有三态定位(可执行同级/npm dist/src 源码) |
| **模块加载器** | 动态导入处理器模块,解析导出函数,处理缓存隔离 | 不可变来源跳过缓存破坏,可变来源按文件元数据破坏 |
| **事件总线注册** | 把处理器按事件类型注册,即发即忘调度执行 | 有界并发 16、有界队列 256、超时 2 秒 |
| **安装服务** | 从 npm 规格或本地归档安装 Hook 包,写安装记录 | 安装前安全扫描,记录完整性漂移,1MB 描述文件上限 |
| **更新服务** | 检测版本漂移,重新安装,刷新配置与记录 | 复用安装服务,报告每个包的更新/未变/跳过/错误状态 |

```
   ┌─────────────────────────────────────────────────────────────┐
   │  模块加载器缓存隔离策略                                    │
   ├─────────────────────────────────────────────────────────────┤
   │                                                             │
   │  模式 A:不可变来源(打包内置)                             │

   │  └─────────────────────────────────────────────┘           │
   │                                                             │
   │  模式 B:可变来源(插件/托管/工作区)                       │

   │                                                             │
   └─────────────────────────────────────────────────────────────┘

   ┌─────────────────────────────────────────────┐
   │ 所有来源都加缓存破坏 → 内置 Hook 每次重启    │
```

## 关键设计约束

### 1. 打包内置目录有三态定位

- **为什么**:OpenClaw 可能以三种形态运行(bun 编译单文件 / npm 安装 / 开发源码),每种形态的内置 Hook 目录位置不同
- **怎么做**:按环境变量覆盖 → 可执行同级 → npm dist → 源码 src 的顺序定位,第一个存在的目录胜出
- **影响**:同一份代码在不同部署形态下都能找到内置 Hook,无需配置

### 2. 不可变来源跳过缓存破坏

- **为什么**:打包内置 Hook 在两次安装间不变,加缓存破坏会让 V8 每次重启重新编译,拖慢启动
- **怎么做**:导入 URL 构建器对打包内置来源不附加查询参数,其他来源按文件修改时间与大小生成缓存键
- **影响**:Gateway 重启时内置 Hook 复用模块缓存,可变来源的编辑能被正确感知

### 3. 工作区与托管来源加载时必须警告

- **为什么**:这两类来源是本地受信代码,直接加载进 Gateway 进程,用户需知情
- **怎么做**:加载工作区或托管来源时打子系统日志警告,标注是受信本地代码
- **影响**:用户从日志能看到本地代码被加载,不会静默执行

### 4. 安装记录只存机器状态不存文件

- **为什么**:安装记录需跨进程重启可见,但状态层规则禁止 JSON/sidecar 文件存运行时状态
- **怎么做**:安装记录写入共享状态库的机器状态表,运行时只读规范记录
- **影响**:卸载/更新以机器状态为准,Doctor 可直接查询而非扫描文件系统

### 5. 安装前必须安全扫描

- **为什么**:Hook 包可能来自不可信 npm 源,需防止恶意包
- **怎么做**:安装服务调用安全扫描器扫描包依赖树,应用安装安全策略,检测完整性漂移
- **影响**:扫描不通过则拒绝安装,完整性漂移被记录供运维审查

### 6. 即发即忘执行有三道界

- **为什么**:Hook 是延伸逻辑,不能拖垮 Gateway
- **怎么做**:有界并发(16)、有界队列(256)、超时(2 秒),队列满则丢弃
- **影响**:Hook 执行失败/超时/丢弃只影响自身,不影响 Agent 回复或消息投递

## 设计观察

### 为什么不统一用一个加载入口

```
错误设计:
   所有来源走同一个目录扫描器 → 内置/插件/托管/工作区
   的定位逻辑差异大,塞进一个函数会变成大分支

正确设计:
   ┌──────────────┐  ┌──────────────┐
   │ 打包内置定位 │  │ 插件 Hook    │
   │ (三态定位)  │  │ (从 manifest)│
   └──────┬───────┘  └──────┬───────┘
          │                 │
   ┌──────┴───────┐  ┌──────┴───────┐
   │ 工作区解析   │  │ 托管目录扫描 │
   │ (realpath)   │  │ (包清单)     │
   └──────┬───────┘  └──────┬───────┘
          │                 │
          └────────┬────────┘
                   │
                   ▼
          ┌─────────────────┐
          │  统一合并 +     │
          │  策略裁决       │
          └─────────────────┘
   • 每个来源有独立定位逻辑,职责清晰
   • 合并后统一走策略裁决(配置与策略层)
   • 新增来源只需加定位器,不改合并逻辑
```

### 为什么描述文件解析与包清单解析分离

```
错误设计:
   把包清单(package.json)的 Hook 声明与描述文件
   (HOOK.md)的前置块混在一起解析 → 两个格式耦合

正确设计:
   ┌──────────────────────────────┐
   │  包清单解析                  │
   │  • 提取包名/版本/依赖        │
   │  • 提取 Hook 列表声明        │
   │  • 判断包类别                │
   └──────────────┬───────────────┘
                  │ Hook 列表
                  ▼
   ┌──────────────────────────────┐
   │  描述文件前置块解析          │
   │  • 逐个 Hook 解析 HOOK.md    │
   │  • 提取事件/OS/依赖/安装规格 │
   │  • 1MB 上限                  │
   └──────────────────────────────┘
   • 包清单告诉你"有哪些 Hook"
   • 描述文件告诉你"每个 Hook 的元数据"
   • 两者职责不同,格式不同,解析分离
```

### 为什么更新服务复用安装服务

```
错误设计:
   更新服务自己实现安装逻辑
   → 安装与更新的代码两套,行为漂移
   → 安全扫描/描述文件解析逻辑重复

正确设计:
   ┌──────────────────────────────┐
   │  更新服务                    │
   │  • 只负责:检测漂移          │
   │  • 调用安装服务(update 模式)│
   │  • 汇总结果                  │
   └──────────────┬───────────────┘
                  │ 复用
                  ▼
   ┌──────────────────────────────┐
   │  安装服务                    │
   │  • 安全扫描                  │
   │  • 包清单解析                │
   │  • 描述文件解析              │
   │  • 写安装记录                │
   └──────────────────────────────┘
   • 单一安装路径,行为一致
   • 更新只是"以新版本再装一次"
   • 完整性漂移在安装服务中统一检测
```
