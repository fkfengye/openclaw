# 03 — Gmail 平台集成

> 读完本章你将理解:Gmail 平台集成作为 Hook 系统的特定实现如何运作、OAuth 设置与 Pub/Sub 订阅如何建立、观察器进程如何随 Gateway 启动与续订、以及平台命令如何把外部工具(gcloud / gog)编排成可复现的设置流程。

## 一句话定位

Gmail 平台集成是 Hook 系统的**端到端平台实现**:
- 把 Gmail OAuth、Pub/Sub 订阅、本地推送端点、观察器进程编排成一条完整链路
- 依赖外部二进制(gcloud / gog),通过设置工具确保依赖就绪
- 观察器随 Gateway 启动,定期续订,失败自动重启

## 组件清单

Gmail 平台集成由 4 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **配置解析器** | 解析 Gmail 配置块,合并默认值与覆盖,解析 Tailscale 模式 | 默认值集中定义(标签/主题/端口/路径),敏感标志集不记日志 |
| **设置工具** | 确保外部依赖与 gcloud 认证、Pub/Sub 主题与订阅、Tailscale 端点 | 命令输出截断(800 字符),Python 路径缓存 |
| **平台命令** | 运行设置与观察器服务命令,生成令牌,写回配置 | Windows 命令行特殊处理,敏感标志过滤 |
| **观察器生命周期** | 随 Gateway 启动观察器,定期续订,失败重启 | 续订串行(单飞),端口占用分类,环境变量可跳过 |

## 关键设计约束

### 1. 默认值集中定义不散落

- **为什么**:Gmail 集成有大量默认值(标签、主题、端口、路径、续订间隔、字节上限),散落会导致改一处找遍代码
- **怎么做**:所有默认值在配置解析器中集中定义,用户配置覆盖默认值
- **影响**:调整默认值只需改一处,行为一致

### 2. 敏感标志不记日志

- **为什么**:Gmail 命令行可能包含令牌、Hook URL 等敏感信息,记日志会泄露
- **怎么做**:维护敏感标志集(token / hook-url / hook-token),日志过滤这些标志
- **影响**:调试日志不泄露凭据,但非敏感参数仍可见

### 3. 续订必须串行(单飞)

- **为什么**:续订是网络调用,并发续订会重复注册、浪费配额、可能触发限流
- **怎么做**:续订用单飞锁,已有续订在飞则跳过新的续订请求
- **影响**:续订不会并发,定时器触发频率高于续订时长时不会堆积

### 4. 端口占用错误需分类

- **为什么**:观察器绑定的本地端口(默认 8788)可能被占,需区分端口占用与其他启动失败
- **怎么做**:错误分类器检测 stderr 中的地址占用模式,返回可诊断的错误类型
- **影响**:用户看到"端口被占"而非模糊的"启动失败",能针对性修复

### 5. 环境变量可跳过观察器启动

- **为什么**:测试与本地恢复路径需要不启动长期观察器,但仍走 Gateway 启动流程
- **怎么做**:设置跳过环境变量,观察器生命周期入口检查并跳过,回调通知
- **影响**:测试可隔离观察器,不影响其他启动逻辑

### 6. Windows 命令行特殊处理

- **为什么**:Windows 的命令行构建与 Unix 不同,批处理命令需特殊解析
- **怎么做**:平台命令在 Windows 上用专门的命令行构建器,受信批处理命令走专用解析
- **影响**:Gmail 集成在 Windows 上能正确调用 gog / gcloud

## 设计观察

### 为什么观察器是子进程而非线程

```
错误设计:
   在 Gateway 进程内跑观察器线程
   → gog 是外部二进制,本就是进程
   → 线程模型无法直接调用 gog
   → 观察器崩溃影响 Gateway 稳定性

正确设计:
   ┌──────────────────────────────┐
   │  Gateway 进程                │
   │  • 观察器生命周期管理        │
   │  • spawn 子进程              │
   │  • 监听子进程 stderr         │
   │  • 崩溃重启                  │
   └──────────────┬───────────────┘
                  │ spawn
                  ▼
   ┌──────────────────────────────┐
   │  gog 子进程                  │
   │  • gmail watch serve         │
   │  • 接收 Gmail 推送           │
   │  • 转发到 Hook               │
   └──────────────────────────────┘
   • 进程隔离,崩溃不波及 Gateway
   • gog 本就是外部二进制,进程模型天然契合
   • 生命周期管理(启动/停止/重启)清晰
```

### 为什么续订用单飞而非队列

```
场景:续订间隔 12 小时,但定时器可能因事件重置多次触发

错误设计:
   每次触发都排队续订
   → 12 小时内堆积多次续订
   → 浪费 Gmail API 配额
   → 可能触发限流

正确设计:
   ┌─────────────────────────────────────────────┐
   │  续订触发                                   │
   │       │                                     │
   │       ▼                                     │
   │  单飞检查                                   │
   │  • 已有续订在飞 → 跳过(不排队)           │
   │  • 无 → 执行续订                            │
   │       │                                     │
   │       ▼                                     │
   │  续订完成                                   │
   │  • 清除单飞标志                             │
   │  • 等下次定时                               │
   └─────────────────────────────────────────────┘
   • 续订是幂等的(重复注册无副作用)
   • 单飞足够,无需队列
   • 节省 API 配额
```

### 为什么设置工具要截断命令输出

```
场景:gcloud 命令失败,stderr 输出数千行调试信息

错误设计:
   完整记日志 → 日志爆炸,难定位关键错误

正确设计:
   ┌─────────────────────────────────────────────┐
   │  设置工具命令执行                           │
   │  • 调用 gcloud / gog                       │
   │  • 捕获 stdout + stderr                    │
   │  • 截断到 800 字符                          │
   │  • 格式化:命令 + 状态码 + 截断输出         │
   └─────────────────────────────────────────────┘
   • 日志保持可读
   • 关键错误信息(通常在前几行)保留
   • 调试时可手动重跑命令看完整输出
```
