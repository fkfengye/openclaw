# 00 — 定时任务组件全景

> 这是定时任务子目录的入口。读完本章你将理解:定时任务是什么、由哪些组件构成、组件之间如何协作、一次定时触发的完整旅程如何走完。

## 一句话定位

定时任务是 OpenClaw 的"自动心跳":
- 按用户配置的时间表自动触发 Agent 会话或外部脚本
- 全部状态(任务、运行记录、心跳、投递计划)落 SQLite,无内存态泄漏
- 调度、存储、投递、退出监控四个职责清晰分层,通过 SDK 边界接入核心
- 状态层依赖共享状态库 + Per-Agent 状态库,会话身份依赖 Agent 会话系统

## 组件清单

定时任务子系统由 4 类核心组件协作:

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **调度服务** | 任务总编排:加/改/删/列/触发,持有可变调度器状态 | 通过锁内操作助手实现,所有变更走单一 facade |
| **调度策略** | 时间表解析、规范化、节奏钳制、错峰偏移、活跃任务登记 | 节奏边界最小不超最大,错峰防整点拥塞 |
| **存储层** | 任务表、Schema、类型、Key、行编解码、临时数据 | SQLite 唯一,共享状态库,禁止 JSON/sidecar |
| **投递层** | 投递执行、投递计划解析、失败通知、重试分类 | 重试分类必须区分执行前后,非幂等工具不重试 |
| **退出监控** | 监听外部脚本进程退出、流式触发任务生命周期 | 直连进程监管器,stop 原因走单一契约 |

### 四层职责边界

```
错误设计(职责混乱):
   调度服务 ──直接调用──► 渠道平台
   调度服务 ──直接操作──► 进程退出监听
   → 调度逻辑与投递、退出监控耦合 → 难测试、难替换

正确设计(分层):
   调度服务 ──► 存储层 ──► 投递层 ──► 渠道系统
                ▲
                │
        退出监控 ──► 调度服务(通知任务终态)
```

## 协作流程

### 一次定时触发的完整旅程

下面追踪一次到点触发的 cron 任务,从调度到投递的全过程,标注每步由哪个组件负责。

```
到点触发(系统时钟到达下一次运行时间)
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 调度服务                                                   │
│    时间表组件检测到任务到期                                   │
│    → 锁内操作助手校验任务可运行(未被禁用 / 未在运行)        │
│    → 计算下一次运行时间(经节奏 / 错峰策略调整)              │
│    → 写入存储层(更新任务状态、下一次运行时间)              │
└─────────────────────────────┬────────────────────────────────┘
                              ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 调度策略                                                   │
│    • 节奏策略:对成功运行的下一次提议做最小 / 最大边界钳制    │
│    • 错峰策略:防止多个任务在整点同时触发拥塞                │
│    • 活跃任务表:登记本次运行为活跃,防止重复触发            │
└─────────────────────────────┬────────────────────────────────┘
                              ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 执行路径分叉                                              │
│    ┌─ Agent 任务路径:触发 Agent 会话                        │
│    │  → 加载 agent 配置 / auth profile / 工具表              │
│    │  → 调用 LLM 产出回复                                    │
│    │                                                         │
│    └─ 脚本任务路径:执行外部脚本                            │
│       → 由退出监控组件监听进程退出                           │
│       → 退出码 + 原因回传调度服务                            │
└─────────────────────────────┬────────────────────────────────┘
                              ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 投递层                                                    │
│    投递计划组件解析任务配置                                   │
│    → 决定模式(播报 / 静默 / 仅失败通知)                    │
│    → 解析目标渠道 + 收件人 + 线程                            │
│    → 投递执行器调用渠道系统发送消息                          │
│    → 失败时走重试分类器判断是否可重试                        │
└─────────────────────────────┬────────────────────────────────┘
                              ▼
┌──────────────────────────────────────────────────────────────┐
│ 5. 终态落库                                                  │
│    调度服务收到执行 + 投递结果                                │
│    → 终态归一化(单一入口,禁止重推优先级)                   │
│    → 写入存储层(运行记录、终态、投递状态)                   │
│    → 重新装填时间表(计算下一次触发)                         │
└──────────────────────────────────────────────────────────────┘
```

### 启动时的追赶(catch-up)

```
Gateway 启动
     │
     ▼
┌──────────────────────────────────────────────────────┐
│  调度服务启动                                         │
│  • 从存储层加载所有任务                               │
│  • 检测"启动前已过期"的任务                          │
│  • 错过窗口的策略:跳过 / 立即补跑(按配置)          │
│  • 重装时间表(为每个任务设下一触发点)              │
│  • 退出监控组件接管进行中的流式任务                   │
└──────────────────────────────┬───────────────────────┘
                               ▼
                  调度服务就绪
                  (等待下一次触发)
```

## 关键设计约束

### 1. 状态全部落 SQLite

- **为什么**:进程重启后能恢复任务表、运行记录、活跃任务;无内存态泄漏
- **怎么做**:任务表存共享状态库;运行记录、临时数据、投递计划均落库;禁止 JSON / JSONL / sidecar 文件
- **影响**:调度服务启动时必须做追赶扫描,不能假设内存里有任务

### 2. 终态归一化是硬约束

- **为什么**:防止超时 / 取消 / 错误 / 完成多个信号在不同视角产生不一致终态
- **怎么做**:所有终态信号经单一归一化入口,projections 只读归一化结果
- **影响**:退出监控、执行超时、用户取消都汇入同一归一化器,不各自判断优先级

### 3. 重试分类必须区分执行前后

- **为什么**:执行开始后工具可能产生非幂等副作用,盲目重试会重复执行副作用
- **怎么做**:重试分类器只在"执行未开始"时对会话生命周期错误标记可重试;执行开始后默认不重试
- **影响**:服务器错误类匹配必须严格带 HTTP 上下文,避免误把消息正文里的数字当成服务器错误

### 4. 节奏与错峰防拥塞

- **为什么**:多个任务同时到期会冲击 Agent 会话与 LLM 配额;整点对齐的 cron 表达式容易集体撞车
- **怎么做**:节奏策略对下一次运行时间做最小 / 最大边界钳制;错峰策略对整点对齐的任务做小幅偏移
- **影响**:任务的下一次运行时间可能略晚于纯 cron 表达式计算结果,这是有意为之

### 5. 退出监控走单一 stop 原因契约

- **为什么**:流式触发任务的启停决策分散在多个调用点,stop 原因不一致会导致重装 / 清理逻辑分叉
- **怎么做**:退出监控组件提供单一 stop 原因解析器,所有直接变更与 reconcile 决策走同一契约
- **影响**:新增 stop 场景必须扩展契约,不能各自定义字符串

### 6. 通过 SDK 边界接入核心

- **为什么**:定时任务是扩展能力,核心运行时必须保持插件无关
- **怎么做**:调度服务通过依赖注入接收日志、存储、系统事件入队等能力;不直接 import 核心 src
- **影响**:测试时全部依赖可替换为 stub,无需启动完整 Gateway

## 设计观察

### 为什么退出监控放在网关层而非 cron 子目录

```
错误归位:
   退出监控组件放在 cron 子目录
   → 它需要直接依赖进程监管器(网关层组件)
   → cron 子目录被迫反向依赖网关 → 边界破坏

正确归位:
   退出监控组件放在网关层
   → 在网关层组合进程监管器 + cron 任务身份
   → cron 子目录只提供任务类型与契约,不感知进程监听
```

### 为什么投递计划与投递执行分离

```
耦合设计:
   投递执行器 ──内嵌路由解析──► 渠道系统
   → 投递执行路径无法在不真正发送时预演路由
   → 配置校验、dry-run、预览都得复制一份路由逻辑

分离设计:
   投递计划(纯函数)──解析配置──► 路由计划
   投递执行器 ──读计划──► 渠道系统
   → 配置校验、dry-run、预览直接复用计划解析
   → 执行器只关心"按计划发送"
```

### 为什么活跃任务表是必需的

```
无活跃表:
   任务到期 ──触发──► Agent 会话
   同一任务在 LLM 慢响应期间再次到期 → 重复触发 → 状态竞争

有活跃表:
   任务到期 ──► 检查活跃表 → 已在运行 → 跳过本次 / 排队
                └─► 不在运行 → 登记活跃 → 触发 → 完成后移除
   → 同任务串行,跨任务并发,资源可控
```
