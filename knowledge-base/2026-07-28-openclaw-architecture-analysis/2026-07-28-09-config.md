# 09 — 配置管理

## 9.1 加载流程

[src/config/io.load.ts](file:///d:/DevSpace/person/ai_space/openclaw/src/config/io.load.ts) 的 `loadConfigFromContext`:

```typescript
export async function loadConfigFromContext(context: ConfigLoadContext): Promise<LoadedConfig> {
  const { env, fs, logger, configPath, stateDir, isReload } = context;
  const raw = await readConfigFile(configPath, { fs, logger });
  const migrated = await migrateConfig(raw, { logger, isReload });
  const validated = await validateConfig(migrated, { logger });
  return { config: validated, sourceConfig: raw, configPath };
}
```

三步:`readConfigFile → migrateConfig → validateConfig`。

- 配置源:`~/.openclaw/openclaw.json` + env vars
- 返回 `LoadedConfig`:`{ config, sourceConfig, configPath }`
- `isReload` 标志区分首次加载与热重载

## 9.2 核心原则

AGENTS.md "Architecture" 段:

> Runtime reads canonical config only. No silent compat for old/malformed config keys. If a config change invalidates existing files, add a matching `openclaw doctor --fix` migration. Core/auth config repairs live in core doctor; plugin-owned config repairs live in that plugin's doctor contract (`legacyConfigRules` / `normalizeCompatibilityConfig`).

> Config/env surface bar is high; `openclaw.json` and environment variables are already large. Before adding a config option or env var, first prove existing product behavior, provider selection, defaults, or doctor migration cannot solve it. Prefer removing or consolidating config/env options when touching these surfaces. Core supports only the latest config shape; `openclaw doctor --fix` migrates older shipped shapes into the current one.

**关键约束**:
1. **Runtime 只读 canonical config**,不静默兼容旧/畸形 key。
2. **配置变更需配套 doctor 迁移**:core/auth 修复在 core doctor;plugin 拥有的修复在 plugin doctor contract。
3. **配置表面门槛高**:新增 config option/env var 前,需先证明现有产品行为/provider 选择/defaults/doctor 迁移无法解决。
4. **核心只支持最新 config shape**:旧 shape 由 `openclaw doctor --fix` 迁移。

## 9.3 CLI Setup 流程(公共 API)

AGENTS.md:

> CLI setup flows are public API when external docs, installers, or integrations can copy them. Changes to `openclaw onboard`, `openclaw configure`, their documented flags, non-interactive behavior, or generated config shape are compatibility-sensitive API contract changes; prefer additive flags/aliases, deprecation windows, and backward-preserving migrations over breaking existing snippets.

**关键约束**:
- `openclaw onboard` / `openclaw configure` 的 flags、非交互行为、生成的 config 形状都是**公共 API 契约**
- 外部 docs/installers/integrations 可能复制这些流程
- 变更需:additive flags/aliases + 弃号窗口 + 向后兼容迁移,而非破坏现有 snippets

## 9.4 配置契约

AGENTS.md "Architecture" 段:

> Config contract: exported types, schema/help, metadata, baselines, docs aligned. Retired public keys stay retired; compat in raw migration/doctor only.

**关键**:
- 导出类型、schema/help、metadata、baselines、docs 必须对齐
- 已退役的 public keys 永久退役,只在 raw migration/doctor 中兼容
- 不允许 runtime 读取已退役的 keys

## 9.6 配置元数据稳定性

AGENTS.md "Cache concept":

> Gateway/plugin metadata is process-stable: installs, manifests, catalogs, generated paths, bundled metadata. Changes require restart or explicit owner reload/install/doctor flow.

> Runtime hot paths: no freshness polling (`stat`/`realpath`/JSON reread/hash). Reuse current snapshots, install records, discovery, lookup tables, root scopes, resolved paths.

**关键**:
- Gateway/plugin 元数据在进程内是 stable 的(installs、manifests、catalogs、generated paths、bundled metadata)
- 变更需要 restart 或显式 owner reload/install/doctor flow
- **Runtime hot path 不做 freshness polling**(不 stat、不 realpath、不 JSON reread、不 hash)
- 复用 current snapshots、install records、discovery、lookup tables

## 9.7 关键观察

- **三步加载**:read → migrate → validate,清晰可追溯。
- **核心只支持最新 shape**:旧 shape 由 doctor 迁移,无 runtime shim。
- **CLI setup 是公共 API**:变更需 additive + 弃号窗口,不可破坏。
- **配置表面门槛高**:新增 option 需先证明无法用现有行为解决。
- **热重载不 stat 文件**:元数据 process-stable,重载靠显式 trigger 而非 polling。
- **retired keys 永久退役**:不允许 runtime 读取已退役 keys。
