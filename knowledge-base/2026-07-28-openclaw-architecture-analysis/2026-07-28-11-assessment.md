# 11 — 评估与风险点

实事求是,基于源码证据列出优点、风险与待精读项。

## 11.1 架构优点

### 优点 1:边界清晰,有 AGENTS.md 强约束

- 顶层 [AGENTS.md](file:///d:/DevSpace/person/ai_space/openclaw/AGENTS.md) 定义全局规则
- 每个 scoped 子树有自己的 AGENTS.md:
  - [src/plugins/AGENTS.md](file:///d:/DevSpace/person/ai_space/openclaw/src/plugins/AGENTS.md)
  - [src/channels/AGENTS.md](file:///d:/DevSpace/person/ai_space/openclaw/src/channels/AGENTS.md)
- AGENTS.md "Map" 段明确目录职责与边界规则
- 核心保持插件无关;插件只能通过 `openclaw/plugin-sdk/*` 进入核心

### 优点 2:懒加载贯穿

- Entry fast-path 拦截 `--version`/`--help`([entry.ts L195-L281](file:///d:/DevSpace/person/ai_space/openclaw/src/entry.ts#L195-L281))
- Gateway 启动用 `createLazyRuntimeModule`([server-start.ts L15-23](file:///d:/DevSpace/person/ai_space/openclaw/src/gateway/server-start.ts#L15-L23))
- 插件加载分 control plane(light)与 runtime plane(heavy),discovery 不 eager import runtime barrels
- 通道 hot path 不静态拉 async-only surfaces

### 优点 3:Schema 严格

- TypeBox(`@sinclair/typebox`)定义,非 freeform string
- 13 个 fragment 按领域拆分,避免单文件巨型 schema
- discriminated union 让 impossible states 不可表示(如 `ChannelTurnAdmission` 的 4 种 kind)
- AGENTS.md 强制:"Runtime branching: discriminated unions/closed codes over freeform strings"

### 优点 4:测试覆盖广

- 每个核心模块都有 `*.test.ts`(colocated)
- 关键流程有 `*.e2e.test.ts`
- 专门 contracts 目录(`src/channels/plugins/contracts/`)做 contract test
- AGENTS.md "Tests" 段明确测试要求

### 优点 5:状态统一为 SQLite

- AGENTS.md 明确禁止 JSON/JSONL/TXT/sidecar 文件存运行时状态
- 双层结构(共享 + per-agent)清晰
- 写事务同步 commit 约束严格(BEGIN 前完成 async,写入前重读校验,禁止 await in callback)
- 迁移单一 owner(Doctor),无 dual-write

## 11.2 风险与代价

### 风险 1:文件爆炸,定位成本高

**证据**:
- `src/gateway/` 下 `server-*.ts` 已超 200 个文件
- `server-startup-*.ts` 单独文件 15+ 个(bootstrap、early、post-attach、finish、log、memory、outcomes、plugins、handler-prewarm、session-migration、secret-surfaces、secret-diagnostics、config)
- `src/plugins/` 下 loader-*.ts、registry-*.ts、provider-*.ts 等数百文件
- `src/plugin-sdk/` 数百个 `*-runtime.ts` 文件

**矛盾点**:AGENTS.md 自己规定"Split files around ~700 LOC when clarity/testability improves",但实际拆分粒度远小于 700 LOC(单文件多在 100-300 LOC),这给新开发者定位代码带来成本。

**影响**:新开发者上手需要先建立"文件命名前缀 → 职责"的映射心智模型。

### 风险 2:Schema 演进包袱

**证据**:
- [package.json L4-L9](file:///d:/DevSpace/person/ai_space/openclaw/package.json#L4-L9):`state=6, agent=16`
- 22 次版本演进累积的迁移代码可观:
  - `openclaw-state-db-*-migration.ts` 多个
  - `openclaw-agent-db-session-*-migration.ts` 多个
  - `openclaw-state-db-legacy-backfills.ts`
  - `openclaw-state-db-schema-repair.ts`
  - `openclaw-state-db-operator-approval-migration.ts`
  - `openclaw-state-db-audit-migration.ts`

**缓解**:AGENTS.md 明确不允许 agent 自主 bump schema 版本,需 owner 显式确认。但历史包袱已存在。

**影响**:任何 schema 变更需考虑 6/16 代迁移路径,复杂度累积。

### 风险 3:配置表面巨大

**证据**:
- AGENTS.md 自己承认:"Config/env surface bar is high; `openclaw.json` and environment variables are already large."
- `src/gateway/config-*.ts` 8 个文件 + `server-reload-*.ts` 8 个文件
- 新增 config option 需先证明现有产品行为无法解决

**影响**:配置项难以简化,新增需高门槛证明。

### 风险 4:CLI 兼容约束

**证据**:
- AGENTS.md 明确:`openclaw onboard`、`openclaw configure` 的 flags、非交互行为、生成 config 形状是公共 API 契约
- 外部 docs/installers/integrations 可能复制这些流程
- 变更需 additive flags + 弃号窗口

**影响**:长期演进受限,无法轻易 breaking change。

### 风险 5:Codex 强制约束

**证据**:
- AGENTS.md "Dependency-touching work" 段:任何 Codex 相关工作必须 agent 亲自检查 `../codex` 源码
- subagent 报告、PR 文本、OpenClaw wrappers、generated schemas、memory、prior bot reviews 都不满足该 gate
- 必须克隆 `https://github.com/openai/codex.git` 到 `../codex` 才能 verdict

**影响**:依赖 Codex 协议的变更成本极高,需双仓库同步检查。

### 风险 6:SDK 表面积巨大

**证据**:
- `src/plugin-sdk/` 数百个 `*-runtime.ts` 文件
- 每个 `*-runtime.ts` 都是 SDK 接缝
- AGENTS.md "Plugin SDK exception":shipped external API 需 new API + named compat/deprecation + removal plan

**影响**:SDK 变更影响外部插件作者,需保持向后兼容 + deprecation 窗口。

### 风险 7:Worker 协议未深入

**证据**:
- `packages/gateway-protocol/src/schema/worker-inference.ts`
- `packages/gateway-protocol/src/schema/worker-admission.ts`
- `packages/gateway-protocol/src/schema/worker-protocol-primitives.ts`
- `src/gateway/server-worker-environment-startup.ts`
- `src/gateway/server-worker-placement-startup.ts`

**待精读**:worker 通信协议、placement 算法、environment 隔离细节本次未深入。

### 风险 8:Cron 子系统复杂

**证据**:
- `src/gateway/server-cron-*.ts` 7 个文件(contract、heartbeat-jobs、lazy、notifications、reconciled、stream-output、stream-watchers、exit-watchers)
- `cron-stream-watchers.test-helpers.ts`、`cron-stream-output.interleavings.test.ts` 等多个测试

**待精读**:Cron 任务的持久化与重启恢复路径未逐行精读。

## 11.4 总体判断

**架构成熟度高**:边界清晰、规则严格、测试覆盖、状态统一。AGENTS.md 体现了项目对工程纪律的极致追求(每个 scoped 子树都有 AGENTS.md,每条规则都给出 rationale)。

**主要代价**:
- 文件拆分过细 → 上手成本
- Schema 演进包袱 → 维护成本
- 配置表面巨大 → 简化困难
- CLI/SDK 兼容约束 → 演进受限
- Codex 双仓库检查 → 依赖变更成本高

**适用场景判断**:
- 适合长期维护的多渠道 AI 助手产品
- 不适合快速原型(规则太严、边界太硬)
- 不适合单人维护(规则要求多角色协作:owner、maintainer、reviewer)
- 适合多人协作、长期演进的项目

**对二次开发的建议**:
- 新增插件:严格走 `extensions/<id>/` + plugin-sdk 路径,不碰核心
- 修改核心:先读对应 scoped AGENTS.md,再做 refactor(默认 clean bounded refactor,非最小 patch)
- 新增配置:先证明现有行为无法解决
- 数据库变更:纯 additive 不 bump,破坏性需 owner 确认
- 协议变更:优先 additive,版本 bump 需 owner 确认
